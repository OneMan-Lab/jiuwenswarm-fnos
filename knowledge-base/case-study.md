# 案例：把 JiuwenSwarm 做成 fnOS 原生应用（v1 → v12）

> 文中引用的 `VERIFY-REPORT.md`、`QA-REPORT.md`、`QA-ORIGIN-REVIEW.md`、`DELIVERY-NOTES.md`、`ENTRY-SURVEY.md` 等均为本次项目的内部过程记录，与原始设备输出一样未随本文发布；引用仅用于标明结论来源与可追溯性。

> 一页半的项目简史，供快速理解全貌。**价值不在最终方案，而在"哪些判断被推翻、依据是什么"**。
> 细节出处：`dev-experience.md`（开发）、`verify-experience.md`（设备取证）、`review-experience.md`（审核）。

## 1. 目标与约束

**目标**：把一个现成的 Python 常驻服务（多智能体工作台，前端 SPA + WebSocket，需模型 API Key）打包为 fnOS 原生应用 `.fpk`，从飞牛门户点图标即可用，仅管理员可见。

**约束**：设备只有 `fnos-cli`（无 shell、读不到日志内容、不能升级已装应用、不能带向导卸载）；上游源码仓只读（补丁只能落在构建产物层）；一张 482 MB 的包重装一次就清空用户数据。

## 2. 关键转折点（每次判断被推翻的经过）

| # | 当时认为 | 实际 | 推翻依据 | 落到的设计 |
|---|---|---|---|---|
| 1 | CLI 能装就能升级 | 装不了已装应用：`{"code":10236}`；带 `install_dep_apps` 还被安全闸拦（`requires App Center UI`） | 真机 CLI 输出 `[实测]` | **双包线**：测试包不带依赖行（供 CLI 验运行时），上架包带（供 UI/商店） |
| 2 | 门户白屏是网关或 WS 坏了 | 上游给顶层文档下发 `frame-ancestors 'none'`，iframe 必然被拒 | `curl -sI` 响应头 + 控制台报错 `[实测]` | 改 `'self'`（wheel 层定点替换 + 重算 `RECORD`），并做成构建闸门 |
| 3 | fnOS 网关不支持 WebSocket | 网关支持；是**应用自己**的 Origin 白名单只有回环，设备 IP 不在表内 | 把设备 IP 加进白名单后立刻 101 `[实测]` | 启动时枚举本机网卡 IPv4 并入白名单（首版只解析 `hostname`，多网卡设备只得到一个地址 ⇒ 仍 403） |
| 4 | `/logo.svg` 404 是"桥缺静态资源路由" | 前端写死**站点根** `/logo.svg`，请求根本没到桥，由主站 nginx 直接 404 | 比对两版 wheel 的 `index.html`/`main.js` 各 +16 B，内容是把路径改成 `/app/<app>/logo.svg` `[实测]` | 修前端引用（带前缀）；桥的静态特例只作防御性兜底 |
| 5 | 卸载"清除数据"失败是"删到一半退出" | 脚本**根本没进删除分支** | 四个候选路径都含应用名（白名单必放行）⇒ 若进分支必然全删，而 `app.env`/`home` 都还在；另 `data/` 的 `btim` 等于安装时刻 ⇒ 是平台清的 `[实测]` | 不 `source` target、向导参数归一化、打印原值、fail-open、恒 `exit 0`、路径三重校验 |
| 6 | 版本号相同 ⇒ venv 不用重建 | 补丁改了 wheel 内容但不动版本号 ⇒ 升级用户继续用旧 wheel，修复不生效 | venv 内 `app_web.py` 仍是 `'none'` `[实测]` | venv 记录 wheel sha256，"版本 **且** 指纹"双比对，三处（install/upgrade/start）都查 |
| 7 | 打出来的包就是刚改的代码 | `supervisor.py` 17:24 才改，包 17:06 已构建 ⇒ 设备跑旧文件，整轮排查方向错误 | 包内文件 `grep -c _local_ipv4_addresses` = 0 `[实测]` | **新鲜度闸门**：包内 vs 工作区逐字节 sha256，不一致拒绝交付 |
| 8 | 域名访问不通是"网关不转发 Upgrade" | 上游两层 Origin 校验都只认精确主机名白名单，用户域名不可预知 | 两层校验代码 + 白名单内容 `[静态]` | 桥内"`Origin` 主机 == `Host` 主机"判定 + 把 `Origin` 归一化为回环交上游 |
| 9 | 同源判定用 `Origin == Host` 就够 | nginx 转发时**改写 `Host`**，真主机名只在 `X-Forwarded-Host` | 真机 flag 只有 `match-x-forwarded`，从未出现 `match-host` `[实测]` | `Host` 优先、代理头仅兜底、判不出来放行 + WARN + flag 标记 |
| 10 | 多 `Host` 一律拒绝是必要硬化 | 收益≈0（伪造同源一条 `Host` 就够），代价可能是 100% 拒掉正常反代 | 审查指出误伤场景 + "多 Host 不增加攻击者能力"论证 | 撤回，改为"任一匹配即放行 + 诊断列全"（v13 执行，v12 冻结） |
| 11 | 退出码非 0 才"诚实" | 平台把非 0 判为卸载失败、可能回滚，比残留更糟 | 早期版本 `exit 1` → 平台报卸载失败 `[实测]` | 恒 `exit 0`，结果写日志；并接受"清除数据只能靠文件取证" |

**第 5 与第 8–10 条是同一类教训**：一个"顺滑的故事"（删了一半 / 网关不支持 WS / 语义该对齐）能解释现象，但经不起"若为真，还必然会发生 X"这一问。**证伪靠伴生结果，不靠现象吻合。**

## 3. 最终方案（v12 / `0.2.9-12`）

- **访问模型**：纯统一网关，不声明 `service_port`；入口 `type=iframe`、`path=/app/jiuwenswarm`、`port=""`（真机 `app entry list` 复核一致）。
- **链路**：浏览器 → nginx(5666/5667) 校验登录态 → `app.sock` → **UDS 桥**（只读头部、改写前缀与 `Host`、其余**纯字节转发**）→ `127.0.0.1:15173`（静态页 + `/api`）/ WS 端口。
- **鉴权**：`SO_PEERCRED` → 网关 uid/gid 降级白名单 → `realpath(exe)` 全路径 + root 属主 + 父目录非全局可写 → 管理员门 `X-Trim-Isadmin`；判定在读请求字节之前。
- **WS**：桥内 Origin 同源判定（Host 优先、代理头兜底、判不出放行）+ `Origin` 归一化；每次握手写日志一行 + 0 字节分支 flag + 403 响应体带 reason。
- **运行时**：设备上建 venv，离线 wheelhouse（262 wheel，`--no-index`），git+ 直接 URL 依赖改写为 `name==version`；版本 + wheel sha 双指纹。
- **数据**：`TRIM_PKGVAR/data` 为唯一数据根；平台"手动安装 = 重装并清 `data/`"已写进用户文档；历史残留改名保留。
- **构建**：双 profile（测试包/上架包，manifest 只差一行）+ 三道闸门（补丁 `--check`、包内 vs 工作区逐字节、profile 断言）。
- **真机结果**：安装成功、入口正确、未登录仍 `200 invalid token`、**IP 与域名对话均双向可用**、WS 判定走 `match-x-forwarded`（校验生效未降级）、无 `deny-*` flag。

**审核判定**：**有条件可上架**（不是"可上架"，也不是"不可上架"）——代码侧无未修 P0/P1，剩两条"补证据"的条件。

## 4. 遗留项（交给下一个人）

| 项 | 性质 | 怎么闭环 |
|---|---|---|
| **C1 非管理员伪造 `X-Trim-Isadmin`** | 安全未知项（唯一） | 普通账号同源 `fetch` 带/不带该头，比对 status + 响应体；返回应用内容 ⇒ 不可上架 |
| **C2 卸载清数据真机闭环** | 功能/隐私承诺 | 窗口内（卸载后、重装前）查 `app.env` 不存在；错过窗口只能记「未验证」 |
| **协议层 101 未取得** | 证据等级 | 现为行为证据；不接受写成"已验证 101" |
| **上架包未经真机安装** | 证据覆盖 | 含 `install_dep_apps`，需在应用中心 UI 装一次 |
| **v13 三项**（多 Host 任一匹配 + 诊断列全 / `Origin` 端口越界显式 deny / `Origin` 侧 `@` 与路径校验对称化） | 健壮性与一致性 | 随下一次实质改动一并出包，不为它单独重装（重装会清数据） |
| **flag 细分到具体命中的头**（`match-xfh`/`-xoh`/`-xfs`） | 可观测性 | 网关升级若只保留一个头时需要它判断是否退化 |
| **依赖网关继续注入 `X-Forwarded-Host`** | 平台依赖 | 若不再注入 ⇒ 退化为 `fallback`（功能不退化、flag 可见） |
| **socket 仍 `0666`** | 残余风险 | `setfacl` 可用则收 `0660`；否则材料显式声明 + peer 校验佐证 |
| **升级保留数据通道** | 未验证的能力 | CLI 不能升级、不在商店无更新入口 ⇒ 不对外承诺 |
| **单用户实例不隔离 / `/favicon.png` 404** | 产品与体验 | 已写进 `desc`/README；不影响功能 |

## 5. 如果重做一次，会先做这三件事

1. **先写"可观测性接口"再写业务**：分支 flag 文件名 + 一行结构化日志。设备侧只能看文件名，这是唯一能远程定性的手段（第 8–10 条全靠它定案）。
2. **先定"判据"再定"实现"**：判据必须是"只有该动作才会改变的量"（`app.env` 是否存在），并写明**取证窗口**；否则会在"目录被重建"上反复返工。
3. **先立"证据等级 + 四要素"（包 sha/脚本 sha/账号 uid/原始输出）再开始测**：本项目中所有"差点把旧包结论套到新包"的时刻，都是因为缺其中一项。
