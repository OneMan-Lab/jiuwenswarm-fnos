# 安全审查与质量门禁经验（可复用）

> 来源：JiuwenSwarm 飞牛 fnOS 应用上架前审核全过程（v1 → v12，含 3 次 P0、6 次定向复核、2 次真机验证）
> 用途：给后来做同类审核（安全关键路径、生命周期脚本、上架材料一致性）的人一套**能直接照做**的方法，而不是一堆结论
> 证据等级标注：`[实测]` 真机或本地真实执行输出｜`[静态]` 代码/配置原文可查｜`[推断]` 由前两者推理、无直接观测｜`[未验证]` 缺证据
> 本文所有"本次"指上述项目，涉及具体 sha/路径仅作案例引用

## 0. 先立三条底线

1. **看不到证据的项一律标 `[未验证]`**，不能用"按代码看应该没问题"代替结论。写"未验证"不丢人，写"已验证"而没证据才丢人。
2. **区分"我核到的事实"与"开发/设备同学转述的结果"**。转述要注明来源；转述一律不能升格为实测。
3. **只读审核**：不在设备上做写操作、不改他人工程、不替开发改代码。发现问题交回去，附**可证伪的判据**，而不是附一句"建议修复"。

## 1. 对抗式审查方法：不读代码，跑函数

### 1.1 为什么必须跑

读代码只能证明"作者想到了什么"，跑函数才能证明"实际会怎么判"。本次最典型的教训：一份 400 行的桥层校验，读三遍都"看起来没问题"，构造 18 条输入一跑，**4 处漏放当场上桌**（其中 2 处后来升级为必修）。

### 1.2 怎么做（可复现骨架）

函数级校验逻辑大多可以**脱离服务单独导入**（模块顶层只解析环境变量、不启动服务时尤其容易）：

```python
import importlib.util, sys
spec = importlib.util.spec_from_file_location("m", "app/server/uds_gateway.py")
m = importlib.util.module_from_spec(spec); sys.modules["m"] = m; spec.loader.exec_module(m)

H = lambda v: ("Host", v)
cases = [
    ("域名正常",   "https://nas.example.com", [H("nas.example.com:5667")]),
    ("跨站伪造",   "https://evil.com",        [H("nas.example.com:5667")]),
    ("代理头伪造", "https://evil.com",        [H("nas.example.com"), ("X-Forwarded-Host", "evil.com")]),
    ("双 Host",    "https://evil.com",        [H("nas.example.com"), H("evil.com")]),
    ("@ 混淆",     "https://evil.com",        [H("nas.example.com:5667@evil.com")]),
    ("端口越界",   "https://nas.example.com:99999", [H("nas.example.com:5667")]),
]
for name, origin, headers in cases:
    try:
        print(f"{name:12s}", m._origin_decision(origin, headers))
    except Exception as e:
        print(f"{name:12s} EXC {type(e).__name__}: {e}")
```

三条实践要求：

- **必须打印原始输出**，不要只写"测试通过"。原始输出是别人能复核的唯一凭据。
- **必须包含一条"应当放行"的用例**。只测拒绝的话，一个 `return False` 的桩函数也能"全绿"。
- **把异常也算一种结果**。本次 `Origin: https://host:99999` 触发 `ValueError: Port out of range`，未被函数捕获、靠外层 `except Exception` 关连接——**fail-closed 无安全后果，但拒绝原因在日志里读不出来**，属必须记录的健壮性缺陷。

### 1.3 本次跑出来的 4 类真实漏放（`[实测]`，v11 版）

| 用例 | 实测结果 | 性质 |
|---|---|---|
| `Host: nas.example.com` + `X-Forwarded-Host: evil.com` + `Origin: https://evil.com` | **allow** `match:evil.com` | 判定基准被"任意请求头"稀释 |
| 双 `Host`（nas.example.com + evil.com）+ `Origin: evil.com` | **allow** `match:evil.com` | 多值取"任一匹配"，与上游"Host 必须唯一"语义冲突 |
| `Host: nas.example.com:5667@evil.com` + `Origin: https://evil.com` | **allow** | `urlsplit` 把 userinfo 后的 `evil.com` 当主机名 |
| `Host: 127.0.0.1:15173` + `Origin: evil.com`（判不出基准） | **allow** 且**无任何告警** | 静默失效，最坏形态 |

### 1.4 用例设计清单（照抄可用）

`null` / 空 Origin / 大小写混用 / 尾点 `example.com.` / 默认端口省略 / 端口不同 / 端口越界 / 带路径与查询 / 异常 scheme / `%00` / `@` 混淆 / 反斜杠 / 头内空白 / 双同名头 / 逗号列表值 / IPv6 字面量与回环 / 无 Host / Host 全回环 / 超长值 / 一条合法+一条非法混合。

> 最后一条（**一条合法 + 一条非法**）最容易被漏：实现往往"静默丢弃非法条目"，于是一个攻击者可控值 + 一个正常值同时出现时，日志里什么都看不到。**要求：非法条目必须单独 WARN 打印出来。**

## 2. 防线分工表：不只说明谁防什么，更是"防止误删"

### 2.1 表怎么建

每道防线写四列：`位置 / 真正防住什么 / 不防什么 / 失效时的兜底是谁`。本次成品（节选）：

| # | 防线 | 真正防住的 | 不防的 |
|---|---|---|---|
| 1 | 对端进程校验（SO_PEERCRED + exe/uid 白名单） | 本机非网关进程直连应用 socket | 经网关转发的请求、跨站页面 |
| 2 | 桥层 Origin 同源校验 | **浏览器**从其它站点发起的跨站 WS | 伪造客户端（可任意填 Origin）、DNS rebinding、Host 被改写时的整体失效 |
| 3 | 管理员门（`X-Trim-Isadmin`） | 非管理员使用应用 | 伪造该头的客户端（依赖第 4 道） |
| 4 | 网关注入身份头 + 登录态 | 未登录访问；覆盖客户端自带的身份头 | 本机进程；网关配置错误 |
| 5 | 上游 Origin 两层校验 | 白名单外 Origin | 桥已归一化 Origin，故对真实域名无判断力 |
| 6 | 上游 token 校验 | 无有效 token 的请求 | 持有效会话者的越权 |

### 2.2 表头必须写一句警示（首版漏掉、评审时才补上——属易忽略项）

> **本表的首要用途不是解释，而是防止误删**：任何人要"优化/精简"防线前，必须先确认该道防线的职责是否还有别的防线承担。尤其——**DNS rebinding 是管理员门、网关注入身份头、上游 token 挡住的，不是 Origin 校验**；因此**不能因为"已有 Origin 校验"就撤掉管理员门或放宽 token 校验**。

为什么这句值钱：后来人做"代码瘦身"时，最容易被删的恰恰是"看起来冗余"的第二道、第三道门。表头这句话把"删除"从"代码风格问题"变成"必须举证的决策"。

### 2.3 判据：防线失效可以，失效不可见不行

- 方案 A（一律拒绝）：防御强，但**正常场景 100% 挂**（本次实测网关会把 `Host` 改写为回环，若"只用 Host"就必然全挂）。
- 方案 B（放行 + WARN + 计数 + 标记文件）：功能不挂，失效**可见、可远程诊断**。
- 选 B 的前提是**可观测性做足**：本次用 `logs/ws-origin-last-<branch>.flag` + `ws-origin.log` 一行一握手（origin/host/xfh 全量值 + allow/deny + reason）+ 计数累加。真机上只需 `ls logs/*.flag` 就能判断走了哪条分支，**不需要用户复现、不需要 SSH 抓包**。

> 可观测性是安全设计的一部分，不是"顺便打的日志"。判据：**一个只读文件的能力（甚至只能看到文件名）就要能判断关键分支走向。**

## 3. 弱证据不能冒充强证据

### 3.1 证据等级（本次实际使用的三档）

| 等级 | 定义 | 本次实例 |
|---|---|---|
| **协议证据** | 直接观测到协议层事实 | 浏览器 Network 里 `/ws` 返回 **101** |
| **行为证据** | 只能观测到功能层的"能用/不能用" | 用户报"能发能回"、消息双向收发 |
| **静态/推断** | 代码可查，但未在真实环境观测 | "按代码看这条会被拒" |

**关键纪律**：行为证据 ≠ 协议证据。用户说"能发能回"，说明链路通，但**不能写成"已验证 101"**；反过来，拿不到 101 也不必否定可用性，只需把等级标清。

### 3.2 本次踩过的具体坑

- 同一句"能发能回"在 v6 上成立，但**桥代码在 v11/v12 变过** ⇒ 按"只要该文件 sha 变就必须重测"的规则，v6 证据不得沿用。最后 v12 真机重新取证才升级结论。
- 上线包里 `uds_gateway.py` 的 sha 一变，所有依赖它的安全结论（对端校验、Origin 判定）都要重开。**用"代码路径没改"做减免是可以讨论的，但必须显式写出减免理由与被减免的范围，不能默默沿用。**

### 3.3 证据绑定四要素（缺一项即记"未验证"）

`包 sha256` + `关键脚本 sha256` + `执行账号（含 uid）` + `原始命令与原始输出`。

> 本次有两次因为缺"包 sha256 + 脚本 sha256"的绑定，差点把旧包的结论套到新包上。绑定不是形式主义：**没有 sha 的结论，一周后就无法证明它属于哪个版本。**

### 3.4 一个真实的方法学反面案例（我自己踩的）

为了比对两个包内某文件是否相同，我把 126 MB 的 `app.tgz` 整包解到 `/tmp`。`/tmp` 是 5.8 G tmpfs，解到一半满盘，后续文件变成 0 字节，`sha256sum` 全部返回 `e3b0c442…`（空文件的 sha）。当时差一步就写出"两包内容不同"的错误结论。

**教训与改法**：

- 大文件取证一律**流式**：`tar -xzf pkg -O app.tgz | tar -xzO <member> | sha256sum`，不落盘。
- **必须同时记字节数**；`e3b0c442…` 是"空"的指纹，见到它就说明取证失败，不是结论。
- 只读他人产物时，用项目内临时目录（如 `.qa-tmp/`），用完即删，别碰 `/tmp`、别碰 `/hosttmp` 之类越界路径。

## 4. 需求与实现的一致性审查

审查的对象不止"代码安全吗"，还有"**承诺兑现了吗**"。本次三处实例，都属于"代码看起来没错、但承诺没兑现"。

### 4.1 向导文案承诺 vs 实际行为

- 文案写：卸载时可选「清除全部应用数据（不可恢复）」。
- 实际：参数只认字符串 `"true"`，平台若传 `True/1/yes/on` 就一律当作"保留"；且脚本在 `set -u` 下 `source` 一个已被删除的脚本 → unbound variable → **提前退出，一个文件都没删**。
- **审查方法**：把文案里的每个承诺逐条翻译成"运行期可观测的事实"，再去代码里找对应分支。找不到分支 = 承诺未实现。

### 4.2 面向用户的清理指引是否"可执行"

本次材料里曾有一条"手工清理残留"的命令，两个问题：

1. **写死卷号** `/<VOL>/...`：用户装在其它存储卷上就静默失效（命令成功、什么也没删）。
2. **需要 root**：普通用户执行必然失败，而失败被 `2>/dev/null` 吞掉，于是"无输出 = 已清干净"是**假阴性**。
3. **判据不可靠**：`ls ... 2>/dev/null` 在无权限时也返回空，等于"看不见 = 不存在"。

**改法**：把"主路径"从"手工命令"改成"产品内动作"（升级到含修复的版本后，卸载时勾选清除，零命令）；命令只作为兜底，且必须写清前置条件（root）与**存在性判据**（`[ -e ]` + 明确输出"仍存在"），禁止用"无输出"证明"已删除"。

### 4.3 上架材料 vs 实际实现

对照检查过的项：manifest 字段与实现是否一致（如"仅管理员可用"↔ `require_admin`；`disable_authorization_path=true` ↔ 实现确实不用授权路径）、体积声明（安装后展开 ≈1.5–1.9 GB、升级峰值 ≈3–3.8 GB）是否与构建脚本一致、测试材料（A9/A10）是否真的存在而非"待补"。

> 一致性审查的价值：不产生"新 bug"，但**防止错误信息进入商店详情页**，而错误信息的代价由用户承担（选错存储卷、以为已清数据）。

## 5. 安全判据的取舍原则

### 5.1 核心判据：用 100% 发生的故障，换条件性发生的风险，是负收益

**本次实例（真实且已撤回）**：为防"多个 `Host` 头里挑一个能过的"，一开始规定"多于一个 `Host` 即拒"。

- 收益：≈ 0。攻击者伪造同源**只需发一条**与 `Origin` 相符的 `Host`，根本不需要第二条；而浏览器根本发不出第二条（`Host` 是 Fetch forbidden header，WS 无自定义头入口），真正能造出第二条的只有代理。
- 代价：若反代追加了第二条 `Host`，**所有 WS（含原本可用的 IP 访问）全挂**，用户看到"能开不能用"。
- 结论：收益≈0、代价是 100% 故障 ⇒ 撤回，改为"任一匹配即放行 + 诊断列全"。**这条判断后来由"多 Host 从不增加攻击者能力"这句话定案**——把问题从"要不要防"重定义为"多 Host 能带来什么"，答案是"什么也带不来"。

### 5.2 什么时候可以"降级为可接受残留"

判断三问：

1. 攻击者**是否需要**这个途径？（若已有更简单的等效途径，防它没有意义）
2. 实际利用是否被**后续门**挡住？（如 DNS rebinding 被"域 cookie + 网关注入身份头 + 管理员门 + token"四道门挡住）
3. 失效时**是否可见**？（可见 ⇒ 可接受；不可见 ⇒ 必须改）

三条都答得出来，才可写"知情接受 + 残余风险声明"；答不出来，就当成待修项，不要用"影响不大"糊过去。

### 5.3 阻断 vs P2 的分界线（本次实际用过的口径）

| 情形 | 分级 | 理由 |
|---|---|---|
| 凭据/密钥可能残留（卸载不清数据、`app.env` 未删） | **阻断** | 用户无法自查、影响可长期存在 |
| 权限/身份门可被绕过（伪造管理员头得到应用内容） | **阻断** | 核心承诺（仅管理员）不成立，且应用能执行命令、读写文件 |
| 删除失败被静默（`exit 0` + 只有日志） | **阻断前必须补可观测** | 若平台不展示日志，"清除数据"承诺就不可验证 ⇒ 必须靠"文件是否存在"取证 |
| 端口越界抛异常、靠外层兜底关连接 | P2 | fail-closed，无安全后果，仅日志可读性 |
| `HEAD` 请求带响应体 | P2 | 协议语义瑕疵 |
| 静态资源 404（logo/favicon）/ 地址断言把 VPN、link-local 等非常用地址并入白名单 | P2 | 体验或收敛度问题，不构成可利用面（记残余，不当阻断） |
| 升级路径"版本号相同就跳过重建"导致修复不生效 | **P1（阻断上架前必修）** | 修复交付不出去，等于没修 |

> 分级的锚点不是"严重程度形容词"，而是**后果由谁承担、用户能否自查**。

## 6. 验收条件的设计：条件必须"一条命令能证伪"

### 6.1 "有条件可上架"是什么意思

三选一口径：**当前可上架 / 有条件可上架（列出条件）/ 不可上架**。禁止"修复后可上架"这种留余地表述。

"有条件可上架"= 代码侧无未修 P0/P1，**但存在若干"用一条命令即可证伪"的待证事实**，且这些事实若为负，结论会直接翻成"不可上架"。条件必须写在纸面上，**不能写成"再测测看"**。

### 6.2 本次的两条合格条件（示范）

| 条件 | 怎么证伪（一条命令） | 为负的后果 |
|---|---|---|
| 非管理员伪造身份头 | 普通账号同源 `fetch('/app/x/', {headers:{'X-Trim-Isadmin':'true'}, credentials:'include'})` 与不带头请求**比对 status + 响应体是否相同** | 若返回 200 且拿到应用内容 ⇒ **不可上架** |
| 卸载清数据 | 卸载选"清除"后、**重装之前**，`[ -e $TRIM_PKGVAR/app.env ]` | 若仍存在 ⇒ **不可上架** |

不合格的写法（本次被反复纠正过的）：
- ❌ "卸载后 data 目录不存在"——重装/启动会 `mkdir -p` 重建，判据必然假失败。
- ❌ "看退出码 = 0 就是清干净了"——实现出于平台回滚风险会恒 `exit 0`，退出码不携带删除结果。
- ❌ "用 `ls` 没输出就是没残留"——无权限时也是空输出（假阴性）。

### 6.3 取证窗口：条件真值只在某个时间窗内成立

本次最有价值的一条细化：**"`app.env` 不存在"这个判据只在"卸载完成 → 重装之前"成立**，因为安装脚本会在 `app.env` 缺失时自动探测并重建它。窗口外再查，会得到假阳性/假阴性两种误判。

**通用写法**：每条条件都写三件事——`取证时机（窗口）`、`判据`、`错过窗口时的替代口径`（本次替代口径是"只能查旧数据残留，并以内容/时间戳区分新旧"，并注明"成本高、不推荐"）。

### 6.4 判据要带"三档"而不是"是非"

同一条件常有多档结果，写清楚每档的含义，避免执行者按自己的理解下结论：

- `403` ⇒ 通过（网关已覆盖客户端身份头）
- `200 invalid token` ⇒ 通过（身份缺失被 token 校验兜住）
- `200 + 应用 HTML/JSON` ⇒ **不通过**（核心承诺不成立，改判不可上架）

## 7. 我判错并撤回的地方（保留过程，不只留结论）

> 这一节比结论更有用：它记录"为什么当时那么想"，避免后人重犯，也避免有人把撤回的方案又捡回来。

### 7.1 错误一：把"多 `Host` 即拒"当成必须硬化项

- **当时的想法**：上游要求"Host 必须恰好一个"，那桥层也应该拒绝多值，语义才一致。
- **错在哪**：把"形式一致性"当成了"安全必要性"，没有先问"这条能防住什么"。实际上多 `Host` 不增加攻击者任何能力（一条相符的 Host 就够了），而被代理追加第二条 Host 是**真实存在的正常行为**。
- **推翻依据**：三条链路事实（浏览器发不出第二条 Host；nginx 出站 `proxy_set_header` 只生成一条；桥入站对端被 SO_PEERCRED 限定为网关进程）+ 一条本质论证（多 Host 不增加能力）。
- **改后**：任一匹配即放行、全不匹配才拒，顺序无关，且**诊断必须列出全部 Host 值**（原实现只取第一条，正好在"要判断顺序"时成了盲区）。
- **教训**：**"与上游语义对齐"不是安全理由**。安全理由必须能回答"防住了谁的什么"。

### 7.2 错误二：为了绕开盲区，提出"只取第一条 Host 当基准"

- **当时的想法**：既然浏览器发的 Host 在最前，那就只信第一条，简单可靠。
- **错在哪**：我们在盲区里**根本判断不了**第一条来自浏览器还是代理。若代理把内部 `Host` 放在前面，"取第一条"会把正常用户拒掉——**同一个坑换个位置**。
- **推翻依据**：诊断输出本身就缺"全部值"（`_get(headers,"host")` 只取第一条），在这个前提下谈"顺序"是建立在一个未验证的假设上。
- **改后**：顺序无关 + 诊断列全。
- **教训**：**为了绕开盲区而引入新假设的修法，比不修更危险**，因为它让问题"看起来解决了"。修盲区的第一动作是**补可观测性**，不是改判定。

### 7.3 错误三：把"残余风险"写成硬阻断（socket 权限 `0666`）

- **当时的想法**：应用 socket 权限 `0666` 意味着本机任何用户都能连，直接判"不可上架"。
- **错在哪**：当前物理条件下 `0600` 会连网关都连不上、`0660` 需先知道网关 gid（`chgrp` 权限不足），写"必须改"等于写一个**做不到的条件**，会把"可控残余"与"不可交付"混为一谈。
- **推翻依据**：实际对端校验（SO_PEERCRED + exe/uid 白名单）已使"能连上"不等于"能通过"；风险是"多一个可连的面"，不是"可绕过"。
- **改后**：列为"上架前必须闭环项 + 残余风险声明"（材料里明示 `0666` 与对端校验已生效），不写"不改就不可上架"。
- **教训**：**阻断项必须"可执行"**。写一个当前条件下无法满足的阻断条件，只会让流程卡死，然后被人绕过。

### 7.4 方法错误四：整包解压导致"证据变空"

见 §3.4（`/tmp` 满盘 → 0 字节文件 → 差点误判两包不同）。
**教训**：取证流程本身也要"可证伪"——**记录字节数**，见到 `e3b0c442…` 立即判定取证失败而不是得出结论。

## 8. 可复用清单（每次审核照做）

**开始前**
- [ ] 确认审核对象与版本（工程目录？包？包的 sha256？），一次只审一个版本
- [ ] 确认标尺（官方文档快照版本、"文档未明确"的标注口径）

**静态**
- [ ] 权限/资源声明与实现一致性（运行用户、join-groups、Scope 是否真的用到）
- [ ] 生命周期九脚本：失败是否写日志、是否有 `umask`、删除边界是否有白名单校验（绝对路径 + 应用名下 + 拒绝 `/`）
- [ ] 入口与网关：`gatewayPrefix`/`gatewaySocket` 落点、是否声明 `service_port`、路径穿越防护、可信身份头来源
- [ ] 版本与指纹：修复是否真的会被交付（"版本号相同就跳过重建"是典型陷阱）

**动态（本地）**
- [ ] 对安全关键函数构造 ≥15 条对抗用例，含一条"应放行"、含异常输入
- [ ] 打印原始输出与字节数，禁止整包解压
- [ ] 关键函数与上一版逐函数 sha 比对，明确"哪些没动、哪些动了"

**真机**
- [ ] 每个结论绑定四要素（包 sha、脚本 sha、账号 uid、原始命令输出）
- [ ] 分支可观测：能否只用"看文件名/看一行日志"判断走的是哪条路
- [ ] 取证窗口确认（会不会有后续步骤把证据重建掉）

**交付**
- [ ] 判定三选一，条件可证伪，附改判触发
- [ ] 证据分栏（开发自验 / 真机实测 / 静态推断），不混算
- [ ] 披露义务单独成列（哪些必须写进材料、哪些禁止写）
- [ ] 保留"我一度这么想、为什么撤回"，供后人查阅

## 9. 一句话总结

> **审查的价值不在"找出多少问题"，而在"把每个结论的证据等级、失效条件与兜底路径写清楚"**——让后来人不必重新推理一遍，也不会因为删掉一道"看起来冗余"的门而把系统打开。
