# 飞牛 fnOS 应用开发反模式库

> 格式统一为：**错误做法 → 会出什么现象 → 为什么 → 正确做法**。
> 收录原则：**只把 `[实测]` 升格为规则**；`[推断]` 一律标注前提并降级为"待确认"；带版本的绝对值（字节数、行数）只作为案例样本，不进规则。
> 每条都能对应到具体现象或命令；配套清单见 `checklists.md`，原理见 `fnos-app-playbook.md`。
> 标注：`[实测]` 本项目真机/本机真实执行观察到｜`[经验]` 方法论｜`[规范]` 官方要求（注章节）。

## AP-01 只比版本号做幂等

**错误做法**：`if [ "$(cat VERSION)" = "$INSTALLED_VERSION" ]; then echo "已就绪"; exit 0; fi`

**会出什么现象**：升级/重装后功能修复**不生效**，用户继续看到旧行为；本地测试全绿、设备上仍旧出错。

**为什么** `[实测]`：包的应用版本号来自上游 `VERSION`，与"wheel 内容是否变化"**无关**。本项目 v2→v3 上游版本都是 `0.2.9b5`，但这一版给 wheel 打了 CSP 补丁 ⇒ 只比版本号的实现判定"无需重建"，设备上跑的是带 `frame-ancestors 'none'` 的旧 wheel。任何"在构建产物层打补丁"的方案都会打破"版本号 ⇒ 内容"的假设。

**正确做法**：
```bash
# venv 建好后写指纹；判定条件 = 版本 AND 指纹
jw_wheel_fingerprint   # 记录 wheel 的 sha256 到 venv/.<app>-wheel.sha256
[ "$ver_ok" = 1 ] && [ "$fp_ok" = 1 ] || jw_install_venv
```
- `install` / `upgrade` / `main start` **三处**都做双比对（覆盖"装完没启动"）；
- 跳过与重建**分别打印原因**：`已就绪（sha=…）` / `重建原因：版本变化|wheel sha 变化`；
- 验证新内容真进去了，用**测试标记字符串**，不要用文件时间戳 `[经验]`。

## AP-02 卸载脚本 `source` 已被删除的目录

**错误做法**：
```bash
set -u
. "${TRIM_APPDEST}/server/init_env.sh"    # 卸载阶段 @appcenter/<app> 已被框架删除
```

**会出什么现象**：用户勾选"清除全部应用数据"，平台显示卸载成功，但 `data/`、`app.env`（含模型 API Key）、`home/` **全部还在**。

**为什么** `[实测]`：卸载回调**总在 target 被删之后**运行，`source` 失败 + `set -u` ⇒ `unbound variable` ⇒ 脚本死在第一行。这是**结构性陷阱**，不是笔误。

**正确做法**：
- 卸载脚本**绝不 `source`** target 下任何脚本（把这条写进文件头注释当硬规则）；
- install/upgrade 侧先判存在再 source，缺失时给出明确错误并写 `TRIM_TEMP_LOGFILE`：
```bash
INIT_ENV="${TRIM_APPDEST:-}/server/init_env.sh"
[ -f "${INIT_ENV}" ] || { echo "应用文件不完整：缺少 ${INIT_ENV}" >&2; exit 1; }
. "${INIT_ENV}"
```

## AP-03 删除动作写成 fail-fast

**错误做法**：`rm -rf "$A" && rm -rf "$B" && rm -rf "$C" || exit 1`

**会出什么现象**：`$A` 删不掉（权限/被占用）就整体退出，`$B`/`$C`（往往包含最敏感的 `app.env`）**永远不会被删**；日志只有一行失败。

**为什么** `[实测]`：删除场景的失败是**局部且可预期**的（文件被占用、ACL、只读），而"中止"会把"删了一部分"变成"几乎没删"。注意参数校验与删除动作是**两类**操作，策略必须相反。

**正确做法**：
| 类别 | 策略 | 做法 |
|---|---|---|
| 参数校验（`TRIM_PKGVAR` 空、非绝对路径、路径越界） | **fail-fast** | `abort`，此时**尚未删除任何东西** |
| 删除动作（单项 `rm` 失败） | **fail-open** | `WARN` + 记入 `RESIDUAL`，继续下一项，最后汇总 |

顺序：隐私优先 `app.env` → `home` → `data` → 运行期目录；汇总写 `TRIM_TEMP_LOGFILE`。

## AP-04 CSP 硬编码 `frame-ancestors 'none'`

**错误做法**：应用给所有文档下发 `Content-Security-Policy: frame-ancestors 'none'`（或直接照抄上游默认）。

**会出什么现象**：直接访问 `http://<设备>:5666/app/<app>` **正常**；从飞牛门户点图标（iframe 嵌入）**白屏**。控制台唯一有效线索：`Framing '…' violates … "frame-ancestors 'none'"`。

**为什么** `[实测]`：门户用 iframe 嵌入应用；`'none'` 禁止任何页面嵌入 ⇒ 必然白屏。**"顶层能开 + iframe 打不开"这个组合本身就是判据**：与网关、端口、WS、前端路由全部无关。

**正确做法**：
- 把顶层文档策略改为 `frame-ancestors 'self'`（"只允许同源嵌入，其余不变"的最小改动）；
- 若源码只读，就在**构建产物（wheel）层**定点替换，并**重算 `RECORD`**（sha256 + size），否则 pip 报 hash 不匹配；
- 不要改用 `sandbox …` 那个分支：缺 `allow-same-origin` ⇒ 文档进入 opaque origin，cookie/localStorage 读不到，登录态会以更诡异的方式坏掉 `[经验]`；
- **不要靠补 `connect-src` 解决**：该策略本来就没有 `connect-src`（WS/API 本不受约束），补它只是收紧，且部分旧浏览器不把 `'self'` 映射到 `ws://` ⇒ 可能反而把 WS 拦断 `[实测]`。

## AP-05 依赖客户端 `Host` 做同源校验

**错误做法**：WS 握手时判 `Origin 主机 == Host 主机` 即认为同源；或用 `Host` 拼绝对 URL / 回调地址 / CSP 源。

**会出什么现象**：**IP 访问与域名访问一起 403**（"页面能开、消息发不出"）；或生成的链接指向 `127.0.0.1`。

**为什么** `[实测]`：fnOS nginx 转发到 UDS 桥时把 `Host` **改写为回环/内部地址**，原始主机名只出现在 `X-Forwarded-Host` 一类代理头里。真机证据：`logs/ws-origin-last-match-x-forwarded.flag` 出现，`match-host` **从未出现**。这不是推断，是分支标记的唯一解。

**正确做法**：
- 判定基准分层：`Host` 恰好一条且可信时优先；代理头（`X-Forwarded-Host` / `X-Original-Host` / `X-Forwarded-Server`）**仅在 `Host` 缺失或全为回环时兜底**（否则 `Host: nas.example.com` + `XFH: evil.com` 会把基准稀释到任意请求头）；
- 判不出基准时**放行 + WARN + 计数 + flag**，绝不让新校验成为"功能唯一依赖未验证假设"；
- `Host` 含 `@` / 路径 / 空白一律拒（`nas.example.com:5667@evil.com` 会被 `urlsplit` 解析成 `evil.com`）；
- **凡是"按 Host 生成 URL/白名单"的设计，在本平台一律不要提** `[实测]`。

## AP-06 用 HTTP 200 判断"成功 / 未授权 / 存在"

**错误做法**：验收脚本 `[ "$(curl -o /dev/null -w '%{http_code}' …)" = "200" ] && echo 正常`。

**会出什么现象**：未登录访问被测成"页面正常"；不存在的应用被测成"存在"；WS 握手"通过"。

**为什么** `[实测]`：未登录访问 `/app/<app>`、`/app/<app>/ws`、**甚至 `/app/doesnotexist`**，一律 `HTTP 200` + `text/plain` + `Content-Length: 13` + body `invalid token`（前缀级兜底）。补齐 `Connection: Upgrade` 等头后仍是 `200` ⇒ **鉴权先于桥**，没有会话拿不到 101。

**正确做法**：判据至少三项——**响应体**（是否含 `invalid token`）、`Content-Length`、`Content-Type`；再加 `Server` 头判"谁返回的"：
- `Server: nginx` ⇒ 请求没到应用（主站/网关处理）；
- **无 `Server` 头** ⇒ 自建桥自己拼的 23 行式响应 `[实测]`。

## AP-07 用 `ls` 空输出判断"已删除 / 不存在"

**错误做法**：`ls "$path" 2>/dev/null` 没输出 ⇒ 判定"已删除"；`file ls-dir <app 私有目录>` 返回 `[]` ⇒ 判定"目录不存在/无权限"。

**会出什么现象**：无权限时也是空输出（**假阴性**）；真实存在的目录被判成"不存在"；把工具的口径问题升级成"设备限制"。

**为什么** `[实测]`：`file ls-dir` 对 app 私有目录会**过滤成空**（`/<VOL>/@appdata/<app>` 同路径用 `file ls` 能正常列出）；`file ls <app 根>` 还会**漏项**（实际存在的 `data/ venv/ run/ logs/` 没列出来）；`ls` 在无权限时与"不存在"同形。

**正确做法**：
- 判"文件是否存在"：`file prop <具体文件路径>`，非 `errno` 即存在——**直指文件，不靠目录列举**；
- 列目录用 `file ls`（不是 `ls-dir`）；
- 删除判据用 `[ -e ]` 并**显式打印"仍存在"**，禁止用"无输出"证明"已删除"；
- 偶发 `errno 4100`（假阴性）时换时间点/换命令重试再下结论 `[实测]`。

## AP-08 拿行为证据当协议证据

**错误做法**：用户说"能发能回 / 聊天正常" ⇒ 在交付文档写"WebSocket 已验证 101"；反之，拿不到 101 就写"WS 不可用"。

**会出什么现象**：材料里出现无法回溯的强结论；审核方一查就发现"你并没有协议层证据"；或者反过来把可用功能判死。

**为什么** `[实测]`+`[经验]`：未登录/无会话时请求在网关鉴权层就被拦（`200 invalid token`），**本侧从未取得协议层证据**。"能发能回"是**功能证据**，101 是**协议证据**，二者不能互相替代。

**正确做法**：三档标注并写清——
| 等级 | 定义 | 允许的表述 |
|---|---|---|
| 协议证据 | DevTools 看到 `101` | "已验证 WS 协议升级" |
| 行为证据 | 双向收发成功 | "WS 链路可用（行为证据，101 未取得）" |
| 静态/推断 | 代码可查 | "按代码看会放行" |

并且：**同一结论换了包就作废**（本项目 v6 的"能发能回"不能沿用到 v11/v12，因为桥代码变过）`[实测]`。

## AP-09 拿"目录不存在"当"清除数据"判据

**错误做法**：卸载后判 `$TRIM_PKGVAR/data`、`$TRIM_PKGHOME` 不存在 ⇒ 认定清除成功；或重装后去看这两个目录。

**会出什么现象**：**任何一次正确的卸载都被判成失败（假阳性）**，然后大家去修一个没坏的地方；或反过来，平台把 `data/` 清了却被判成"没清干净"。

**为什么** `[实测]`：`install_callback` 与 `runtime.sh` 都对 `JW_DATA`、`JW_LOGS`、`JW_RUN`、`TRIM_PKGHOME`、`TRIM_PKGTMP` 执行 `mkdir -p` ⇒ 重装/首次启动后这些目录**必然重建（内容为空）**。

**正确做法**：
> 判据：**卸载完成 → 重装之前**，`$TRIM_PKGVAR/app.env` **不存在**（且 `$TRIM_PKGVAR` 空或不存在）。

- `app.env` 是干净探针：没有常规创建点，只在"文件不存在时"由 `install_callback` 探测生成一次；
- **但它在重装时会被自动重建** ⇒ 判据只在**窗口内**有效，窗口外只能查旧数据残留并标「未验证」；
- 不要用退出码代替结果（见 AP-12）。

## AP-10 用进程名 / `comm` / `basename` 判身份

**错误做法**：可信对端判定写成 `comm == "nginx"` 或 `basename(exe) == "nginx"`。

**会出什么现象**：本机任意用户执行 `cp /usr/bin/python3 /tmp/nginx && /tmp/nginx` 直连应用 socket 即被放行 ⇒ "仅管理员可用"的整条信任链被绕过。

**为什么** `[实测]`：`comm` 可被 `prctl(PR_SET_NAME)` 任意改名（且只有 16 字节）；`basename` 只看最后一段，`/tmp/nginx` 就够；两者都只是"自报家门"。

**正确做法**：`SO_PEERCRED`（内核填，不可伪造）取 uid/gid/pid → `realpath(/proc/<pid>/exe)` **全路径** glob 匹配 → 要求 `st_uid == 0` → 要求父目录 `mode & 0o002 == 0` → 以上任一不满足即 deny；`comm` **只写日志**。跨用户读 `/proc/<pid>/exe` 会 `EACCES`，需要"网关 uid 降级白名单"兜底（探测写 `app.env`，并显式 `chown` 给应用用户，否则解析器 `-O` 校验会让它**静默失效**）`[实测]`。

## AP-11 socket 直接改 `0600`

**错误做法**：看到 socket 是 `0666`，直接 `chmod 0600`（或 `chown` 改属组收紧到 `0660`）。

**会出什么现象**：网关自己连不上 ⇒ 入口 502/403；或者"配置了 gid 也不生效"，间歇性 502/403（多 worker 组时）。

**为什么** `[实测]`：网关 worker 与 app **是不同 uid**（本项目 app uid <APP_UID>，网关侧 <GW_UID> 一类）⇒ `0600` 把网关锁在外面；而 `chgrp` 要求"root 或本身是该组成员"，`privilege` 里没有 `join-groups` ⇒ `chown(..., -1, gid)` **必定 EPERM**；socket 只能绑一个组，两个 worker 组时会间歇失败。

**正确做法**：`0660` + `setfacl -m g:<gid>:rw <sock>`（属主可对任意组授权，不需要自己是成员，天然支持多组）；`setfacl` 缺失或失败 ⇒ **回退 `0666` + WARN**，不拒绝服务；`chmod` 必须在 `start_unix_server()` **之后**（否则被 `umask` 覆盖）。若最终仍是 `0666`，把它写成"必闭环项 + 残余风险声明"，不要写成做不到的硬阻断。

## AP-12 卸载脚本 `exit 1` 表示"出错了"

**错误做法**：删除失败/参数异常时 `exit 1`，觉得"更诚实"。

**会出什么现象**：平台把非 0 判为**卸载失败**并可能回滚/报错，缺陷从"删一半"升级成"用户以为没卸掉"；而删除结果反而没人看。

**为什么** `[实测]`：卸载回调的退出码语义是"卸载流程是否成功"，不是"清理是否彻底"。本项目早期版本 `exit 1` 直接导致平台判卸载失败。

**正确做法**：**始终 `exit 0`**（参数非法导致"未删任何东西"的 `abort` 除外），把"删了 N 项 / 残留 M 项 + 原因"写进 `TRIM_TEMP_LOGFILE`。
**副作用要一起接受**：删除失败会变成"静默"，而平台不一定展示卸载日志 ⇒ 所以"清除数据"只能靠**文件是否存在**取证，不能看退出码。

## AP-13 补丁匹配不到就"跳过并继续构建"

**错误做法**：`patch.py` 找不到目标常量时 `print("skip"); sys.exit(0)`。

**会出什么现象**：包照常打出来、能装、版本号是新的，但**修复根本没进去**；审核/用户看到的是"新版本还是旧问题"。

**为什么** `[经验]`：上游只要改一下写法（常量重命名、移到别的文件），补丁就静默失效。"能构建成功"与"包是对的"之间必须有一个**能失败的**独立校验。

**正确做法**：补丁脚本提供 `--check`（断言已生效），**匹配不到/出现多次即 `exit 1`**；构建脚本把"打补丁 + `--check`"做成前置闸门；再加两道独立闸门：
1. **新鲜度**：解包 `app.tgz`，把 `cmd/*`、`app/ui/config`、`app/server/*`、`wheelhouse/*.whl` 与工作区**逐字节 sha256** 比对，不一致即中止；
2. **profile 断言**：测试包必须无 `install_dep_apps`，上架包必须有。

## AP-14 整包解压取证 / 依赖 `/tmp`

**错误做法**：为了比对两个包里的某个文件，把 126 MB 的 `app.tgz` 整体解到 `/tmp` 再 `sha256sum`。

**会出什么现象**：`/tmp`（本项目 5.8 G tmpfs）写满 ⇒ 后续文件变 **0 字节** ⇒ `sha256sum` 全部返回 `e3b0c442…`（空文件指纹）⇒ 差点写出"两包内容不同"的错误结论。

**为什么** `[实测]`：整包解压的空间需求 = 解压后总量，且失败是**部分成功**（前几个文件看起来正常）。

**正确做法**：
- 大文件一律**流式**：`tar -xzO <member> | sha256sum`，不落盘；
- **必须同时记字节数**；见到 `e3b0c442…` 立即判"取证失败"，不是结论；
- 用项目内临时目录（如 `.qa-tmp/`），用完即删；构建/解包都显式指定大分区 `TMPDIR`。

## AP-15 用日志行字节数反推走了哪个分支

**错误做法**：不同分支的日志行长度不同，于是用文件 `size` 增量反推"走了哪一支"。

**会出什么现象**：结论时对时错，且无法复核；改一次白名单就"证明"了完全相反的结论。

**为什么** `[实测]`：三个分支行长为 155 / 157 / 154 B，**只差 1–3 B**，而 `Host` 真值未知、连接数不定 ⇒ 总量漂移远大于信号。差分法只在"差异显著且可枚举"时成立。

**正确做法**：把分支**编码进文件名**——每次判定覆盖写一个 0 字节文件 `logs/<topic>-last-<branch>.flag`，`file ls` 列出文件名即可判分支（本项目正是靠 `ws-origin-last-match-x-forwarded.flag` 才确认"网关改写了 `Host`"）。
配套：分支名互斥且自解释；写新标记前先删旧标记（否则会误读成"多个分支都发生过"）。

## AP-16 把"工具空结果"当"设备事实"

**错误做法**：`file ls-dir /<VOL>/@appmeta/<app>` 返回 `[]` ⇒ 结论"ACL/属主限制，读不到元数据"；目录列举没看到 `data/` ⇒ 结论"数据目录不存在"。

**会出什么现象**：整条结论链建立在工具口径上；后面换了命令发现对象一直都在，前面所有推理作废；极端情况下据此改代码去"修"一个不存在的问题。

**为什么** `[实测]`：`ls-dir` 对 app 私有目录会过滤成空，换 `file ls` 就正常；`file ls <app 根>` 还会漏项（`data/ venv/ run/ logs/` 没列出来）；`file search` 只匹配**文件名**，不能当内容探针。

**正确做法**：**工具的"空结果"只能产出"未验证"，不能产出"不存在"**。先换等价命令复核（`ls-dir` → `ls`、目录 → 具体文件 `file prop`），再下结论；结论里写清用的是哪条命令。

## AP-17 安全用例只写"应拒绝"

**错误做法**：给安全函数写 10 条跨站/伪造用例，全部断言 `False`；跑完全绿就认为"校验没问题"。

**会出什么现象**：一个 `return False` 的桩函数也能全绿；真正该放行的正常访问挂了却没人发现。

**为什么** `[实测]`：本项目把 400 行校验逻辑"读三遍都觉得没问题"，构造 18 条输入一跑，**4 处漏放当场上桌**（其中 2 处后来升级为必修）。

**正确做法**：
- 用例集**必须包含"应当放行"的**（域名正常、IP 正常、大小写、尾点、默认端口省略）；
- **必须打印原始输出**（`name -> (allow, reason, branch)`），不要只写"通过"；
- **把异常也算一种结果**（`Origin: https://host:99999` 触发 `ValueError`，被外层兜住 ⇒ fail-closed 但原因不可读，属必须记录的健壮性缺陷）；
- 必测"**一条合法 + 一条非法混合**"：实现常静默丢弃非法条目，导致攻击者可控值+正常值同时出现时日志里什么都没有。

## AP-18 把"多 `Host` 即拒"当必要硬化

**错误做法**：为了与上游"`Host` 必须恰好一条"的语义对齐，桥层规定"≥2 条 `Host` 一律拒绝"。

**会出什么现象**：若反代/网关在保留原 `Host` 的同时**附加**第二条，**所有 WS 被拒**（包括原本可用的 IP 访问）⇒ 用户看到"能开不能用"，而这正是本轮要消灭的故障形态。

**为什么** `[实测]`+`[经验]`：**多 `Host` 从不增加攻击者能力**——伪造同源只需发一条与 `Origin` 相符的 `Host`；浏览器发不出第二条（`Host` 是 Fetch forbidden header）、nginx 出站 `proxy_set_header` 只生成一条、非网关进程被 peer 校验挡住。所以"即拒"防的是一个**本来就有更简单走法**的攻击：收益≈0，代价可能 100% 故障。

**正确做法**：取全部可解析且非回环的候选，**任一与 `Origin` 主机匹配即放行**，全部不匹配才拒（`reason=multi-host-mismatch(N)`）；顺序无关；**诊断必须列全所有 Host 值**（只取第一条正是盲区成因）；非法条目单独 WARN，不许静默丢弃。
通用判据：**用 100% 发生的故障去换条件性发生的风险，是负收益。**

## AP-19 结论先行："网关不支持 WebSocket"

**错误做法**：`/ws` 握手失败 ⇒ 写进报告"fnOS 统一网关不支持 WS 升级"，并据此改方案（退化成端口型）。

**会出什么现象**：整轮工作方向错误；基于这个"结论"做出的架构决策（开端口、绕过网关、加自建鉴权）全部要回滚。

**为什么** `[实测]`：网关支持 WS 支持得很好，**是应用自己**的 Origin 白名单只有 `127.0.0.1,localhost,none`，设备 IP 不在表内 ⇒ 403。把设备 IP 加进白名单后立刻 101。后来官方文档（`advanced §2`）也明确写明网关支持 WS。

**正确做法**：
- 现象（握手失败）≠ 原因（谁拒的）。先用**归属判据**定位是谁返回的：`Server: nginx` 是主站/网关，**无 `Server` 头**是自建桥；
- 再看应用自身的三层可能：Origin 白名单、base path、CSP；
- 结论写成"**当时证据支持的最强表述 + 未验证项**"，而不是"平台不支持"；一旦有新证据（官方文档、真机 flag），**显式撤回并留档**（本项目把失败结论与撤回依据都保留在报告 §23，供后人查）。

## AP-20 只测 IP 或只测域名

**错误做法**：IP 访问通过就收工；或域名通了就不回归 IP。

**会出什么现象**：本项目先后两次踩同一形态——"IP 能开、域名不能用"；反过来若只测域名，某个版本"IP 反而挂了"也发现不了。

**为什么** `[实测]`：两者的差异只在浏览器发出的 `Origin`/`Host` 主机名；应用侧若做"主机名精确匹配"，域名**一定**不在默认集合里 ⇒ 表现为"只有域名不通"。而 `Host` 被改写后，"只信 Host"的实现会让**两者一起挂**。

**正确做法**：验收顺序固定 **先 IP 后域名**（IP 挂了就不是域名逻辑的问题，别去查域名）；两侧都取 flag 分支证据；跨站否定用例要在**不同 host 的页面**里做（同 host 页面不构成否定用例）。

## 附：判定"这是不是反模式"的三问

1. **它防的是谁的什么？** 答不出来就不是安全措施，是形式一致性（AP-18）。
2. **失效时可见吗？** 不可见 ⇒ 必须改；可见 + 有兜底 ⇒ 可记录为残余风险接受。
