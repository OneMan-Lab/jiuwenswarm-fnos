## 1. 决策树：什么形态的应用配什么访问模型

**这一节解决什么问题**：在写第一行代码之前，把"应用怎么被访问"定下来。定错了，后面所有工作（鉴权、WebSocket、CSP、端口、上架审核）都要返工。

### 1.1 三种模型的能力边界

| 能力 | `index.cgi` | 统一网关 | 独立端口服务 |
|---|---|---|---|
| 简单静态页 | 适合 | 支持 | 支持 |
| 常驻服务 | 不推荐（每请求起进程） | **适合** | 适合 |
| WebSocket | **不支持** | 支持 | 支持 |
| NAS 登录态 | 调用 CGI 前校验 | 转发前校验 + 注入可信头 | **与登录态无关** |
| 常见路径 | `/cgi/ThirdParty/{app}/index.cgi/` | `/app/{app}` | `http://host:port` |
| 额外暴露面 | 无 | 无（复用 5666/5667） | **LAN 裸端口，绕过 fnOS 登录** |

来源：`[规范] advanced §1`；其中"端口型绕过登录"这一点由设备实测确认 → `[实测]`。

### 1.2 设备上的实证分布（决定"平台期望什么"）

`[实测]` `app entry list` 全量 25 条（详见 `ENTRY-SURVEY.md §2.1`）：

- 官方内建应用 **100% 走网关路径**（`/iscsi/`、`/v`、`/p`），**都不声明端口**；
- 第三方 · 网关路径型 6 个（路径形如 `/app/<app>` 或 `/cgi/ThirdParty/<app>/index.cgi`）；
- **`type` 字段不能用来判形态**：有的应用 `type=iframe` 却声明了端口，有的 `type=url` 但走网关路径。**必须看 `uri.port` 与 `uri.path` 的组合** `[实测]`。

### 1.3 决策树（按顺序问四句）

```
Q1 你的应用有 WebSocket / SSE 长连接吗？
   ├─ 有 → 只能是「统一网关」或「独立端口」；index.cgi 直接排除  [规范 advanced §1]
   └─ 无 → 继续

Q2 应用是常驻进程（不是每请求起一次）吗？
   ├─ 是 → 统一网关 / 独立端口
   └─ 否 → index.cgi 也可以，但优先网关（少一套 CGI 约定）

Q3 需要复用 NAS 登录态、要和门户同域、要 iframe 嵌入门户吗？
   ├─ 需要 → 统一网关（唯一选择：只有它在转发前校验登录态并注入 X-Trim-*）
   └─ 不需要 → 独立端口可接受，但要接受两个代价（见下）

Q4 你能接受「LAN 裸端口无鉴权」+「https 门户下 iframe 被混合内容阻断」吗？
   ├─ 能（且应用自带强鉴权）→ 独立端口
   └─ 不能 → 统一网关
```

**本项目结论** `[实测]`+`[经验]`：JiuwenSwarm 是 Python 常驻服务 + WebSocket + 需要 NAS 登录态 ⇒ **纯统一网关，manifest 不声明 `service_port`**。真机 `app entry list` 复核入口为 `type=iframe` / `path=/app/jiuwenswarm` / **`port=""`**，与声明一致。

### 1.4 两个模型各自的"隐性代价"（决策时必须写进方案）

**独立端口型**：

- **无 TLS**：设备上 7 个端口型应用逐个测 `https://IP:port/`，全部 `http_code=000`（TLS 握手失败），`http://` 才 200 ⇒ **端口型只监听明文 HTTP**（7/7）`[实测]`。
- **https 门户下 iframe 会触发混合内容阻断** `[经验，未用浏览器实测]`：门户在 5667（https），iframe 内嵌 `http://IP:port` 会被浏览器拦。
- **完全绕过 fnOS 统一登录**：对 LAN 裸端口可达，无 302、无 `invalid token` `[实测]`。安全责任 100% 落到应用自己。

**统一网关**：

- 必须自己处理 **base path**（前缀改写）——上游服务通常只认根路径；
- 必须自己处理**可信身份头的信任前提**（`X-Trim-Isadmin` 谁都能伪造，只有"对端确实是网关"时才可信，见 §6）；
- 网关会**改写 `Host`**（见 §5.3），任何"按 `Host` 生成 URL / 做校验"的设计都会失效。

### 常见坑

1. **只看 `type` 判形态**：`iframe` 不等于网关型，`url` 也不等于端口型。判据只能是 `uri.port` 是否为空 + `uri.path` 是否带 `/app/<name>` `[实测]`。
2. **给网关型应用又声明 `service_port`**：等于多开一个 LAN 裸端口，把网关的鉴权路径绕过去。规范要求网关型不需要 `service_port` `[规范 advanced §2]`。
3. **以为"端口型更简单"**：省掉的是前缀改写，多出来的是 TLS、混合内容、LAN 无鉴权、登录态关联四件事。
4. **不声明 `os_min_version`**：国内版统一网关要求声明最低系统版本（`[规范 advanced §2]`，示例 `1.1.3100`）。本项目取 `os_min_version=1.1.3100`。

## 2. 应用包与生命周期脚本

**这一节解决什么问题**：把包结构、manifest 关键字段、九个生命周期脚本的触发时机与硬规则钉死，避免"装上了但平台不认"或"卸载时删错东西"。

### 2.1 安装后的目录映射（先记住"哪个目录会被谁重建"）

```
/var/apps/{appname}
├── cmd/        生命周期脚本（9 个）
├── config/     privilege（运行身份）、resource（资源与 Scope）
├── manifest
├── ICON.PNG / ICON_256.PNG
├── target -> /vol{n}/@appcenter/{appname}   应用文件与运行资源（TRIM_APPDEST）
├── etc    -> /vol{n}/@appconf/{appname}       配置（TRIM_PKGETC）
├── var    -> /vol{n}/@appdata/{appname}       持久运行数据（TRIM_PKGVAR）
├── tmp    -> /vol{n}/@apptemp/{appname}       临时（TRIM_PKGTMP）
├── home   -> /vol{n}/@apphome/{appname}       应用用户数据（TRIM_PKGHOME）
└── wizard/      install / upgrade / uninstall / config 表单
```
`[规范] dev-guide §3`。**一律用 `TRIM_*` 变量定位路径，不硬编码 `/var/apps/...`** `[规范] dev-guide §3`。

**关键推论（本项目付过学费）**：

- `data/`、`logs/`、`run/`、`home/` 这些目录会被 `mkdir -p` **重建**（`runtime.sh` 与 `install_callback` 都做）⇒ **"目录不存在"永远不是有效判据**。
- `target/`（`TRIM_APPDEST`）在**卸载阶段已被框架删除** ⇒ 卸载脚本不能 `source` 它下面的任何文件（见 §2.3）。
`[实测]`：详见 `verify-experience.md §3.3`。

### 2.2 manifest 关键字段（只列会"决定能不能用"的）

| 字段 | 取值要点 | 依据 |
|---|---|---|
| `appname` | 唯一标识；建议与入口 ID 前缀、`gatewayPrefix`、socket 名一致 | `[规范] dev-guide §4` |
| `platform` | `x86` / `arm` / `all`；**包内含架构相关二进制（如 cp312 manylinux wheel）就不能写 `all`** | `[规范] dev-guide §4` |
| `os_min_version` | 网关型必须声明 | `[规范] advanced §2` |
| `install_dep_apps` | 依赖应用，`:` 分隔，`>` 声明最低版本；**不递归**，要直接声明全部 | `[规范] advanced §5` |
| `ctl_stop` | 常驻服务 `true`（显示启停）；静态/配置型 `false` | `[规范] dev-guide §4` |
| `checkport` | 有端口服务时默认 `true`；网关型本项目设 `false`（实测无端口可检查） | `[规范] dev-guide §4` |
| `service_port` | **网关型不写**；端口型必写 | `[规范] advanced §2` |
| `disable_authorization_path` | 不需要用户选文件/目录时 `true`，否则授权入口不可用 | `[规范] dev-guide §4` |
| `desktop_applaunchname` | 必须与 `{desktop_uidir}/config` 的入口 ID **完全一致**，否则应用卡片点不开 | `[规范] advanced §3` |
| `changelog` | 升级时面向用户展示，必须非空且说人话 | `[规范] release §4` |

本项目取值 `[实测]`（`0.2.9-12`）：`platform=x86`、`os_min_version=1.1.3100`、`ctl_stop=true`、`checkport=false`、`disable_authorization_path=true`、无 `service_port`。

### 2.3 九个生命周期脚本：触发时机与硬规则

| 脚本 | 触发时机 | 本项目做的唯一一件事 | 硬规则 |
|---|---|---|---|
| `install_init` | 安装文件落地**前** | `exit 0`（此时框架目录/变量尚不完整） | 不要依赖任何框架路径 |
| `install_callback` | 文件落地**后** | 建数据目录 → 准备数据根 → 建 venv（离线 wheel）→ 探测网关 uid 写 `app.env` | **先 `[ -f ]` 再 `source`**；必须**幂等** |
| `main start/stop/status` | 用户/框架启停 | 起 supervisor 进程组，等 socket+health 就绪 | 退出码 `0`成功/`1`失败/`3`=status 未运行 `[规范] dev-guide §8` |
| `upgrade_init` | 升级**前** | `cmd/main stop` | 先停服务，避免旧进程占 socket/端口 |
| `upgrade_callback` | 升级**后** | 重建 venv（数据不动） | 幂等 |
| `uninstall_init` | 卸载**前** | `cmd/main stop` | — |
| `uninstall_callback` | 卸载清理 | 按向导删数据 + 清运行期文件 | **四条硬规则见下** |
| `config_init` / `config_callback` | 配置表单提交前后 | 本项目无表单，`exit 0` | — |

`[规范] dev-guide §8` 给出九个脚本的触发时机；"幂等"是规范明写的（安装/升级/配置流程都可能被重新执行）。

### 2.4 `uninstall_callback` 的四条硬规则（可直接抄）

> **参数校验 fail-fast（防误删）；删除动作 fail-open（能删的尽量删）；退出码永远 `0`（避免平台误判卸载失败）；隐私优先排序（`app.env` → `home` → `data` → 运行期目录）。**
> `[实测]` 来源：`cmd/uninstall_callback` 头注释 + `DELIVERY-NOTES §9.11`。

四条各自对应一次真实故障：

| 规则 | 不遵守会发生什么 | 证据 |
|---|---|---|
| 不 `source` target 下脚本 | 卸载阶段 `TRIM_APPDEST` 已不存在 ⇒ `source` 失败 + `set -u` ⇒ unbound variable ⇒ 脚本死在第一行，**一个文件都没删**，平台仍显示卸载成功 | P0-03 `[实测]` |
| 向导布尔**归一化** | 只认字符串 `"true"`，平台传 `True`/`1`/`yes` 就走"保留数据"分支 ⇒ 用户以为清了，API Key 还在 | `[实测]` |
| 删除动作 fail-open | 第 2 项删除失败即 `exit 1` ⇒ 后面（含最敏感的 `app.env`）永远不删 | `[实测]`+代码复核 |
| 恒 `exit 0` | 非 0 可能触发平台回滚/报错，"删一半"升级成"用户以为没卸掉" | `[实测]` |

**路径安全（容易漏的一层）**：`TRIM_PKGHOME` 可能被平台指到父目录（如 `@apphome` 本身），于是要拼候选 `p/应用名`、`dirname(p)/应用名`——**候选路径必须重新过安全校验**：绝对路径、非 `/`、父目录不能是根、`basename` 必须等于应用名。`[实测]` 注入 `TRIM_PKGHOME=/` 时，未加这层校验会算出 `/jiuwenswarm` 并删除它；加了之后仅 WARN 跳过（`QA-ORIGIN-REVIEW §9.5` 用 `rm` 桩验证 5 个场景）。

### 常见坑

1. **`install_callback` 里假设变量已就绪**：`install_init` 阶段框架目录未完整，不要在里面做任何依赖框架路径的事。
2. **`status` 用"进程在不在"判定**：僵尸/被收养的孙进程会让状态骗人。本项目用 **PID + `/proc/<pid>/cmdline` 含 supervisor 路径 + socket 存在 + HTTP 健康检查** 四重判定 `[实测]`。
3. **失败不写 `TRIM_TEMP_LOGFILE`**：用户只看到"安装失败"，运维无从下手。规范要求失败前写入可执行的错误信息 `[规范] dev-guide §8`。
4. **卸载时删整个 `TRIM_PKGHOME` 目录**：这是规范偏离项（框架约定只删自建子目录）。本项目 0.2.9-12 的实现仍是 `rm -rf` 整个 `@apphome/<app>`，并在 `DELIVERY-NOTES §8` **明确留痕**为"知情的设计偏差"；更稳的做法是"清空内容、保留目录本身"（自测点：目录仍在、`find -mindepth 1` 无输出）。

## 3. 运行时与依赖（含双包线）

**这一节解决什么问题**：让应用在**没有外网、没有系统 pip、设备上只有运行时应用**的环境里装得上、跑得起来，并且升级时真的换到新代码。

### 3.1 依赖声明与 PATH

```ini
# manifest
install_dep_apps=python312        # 或 nodejs_v22 / java-21-openjdk
```
```bash
# 生命周期脚本里，调用运行时命令前先加 PATH
export PATH=/var/apps/python312/target/bin:$PATH
```
`[规范] advanced §7`。多依赖**从右到左**安装启用；依赖检查**不递归**，必须直接声明自己用到的全部依赖 `[规范] advanced §5`。

### 3.2 离线 wheel 集（常驻 Python 服务的实际解法）

本项目做法 `[实测]`：

1. 构建期把应用本体 + 全部依赖打成 wheel，放 `app/wheelhouse/`（本项目 262 个 wheel，`WHEELS.txt` 记录名称/版本/sha256，`SHA256SUMS` 汇总）；
2. **venv 在设备上创建**（用 `python312`），PATH/shebang 天然正确，可随升级重建；
3. `python312` 若缺 `ensurepip`，用 wheelhouse 内 `pip-*.whl` 自举；
4. 安装 `--no-index --find-links wheelhouse`，**绝不联网**。

**踩过的一个坑（必须处理）**：上游 `METADATA` 里有些依赖写成直接 URL（`name @ git+https://…`），**`--no-index` 也拦不住**——pip 会强制回源克隆。解法是构建期把这些条目改写为 `name==<实际 wheel 版本>`（只改 `METADATA`/`RECORD`，不改代码），并逐条打印改写清单 `[实测]`。

### 3.3 依赖声明会把 CLI 安装路径堵死 ⇒ 双包线

**现象** `[实测]`：

- 包内写 `install_dep_apps=python312` 时，`fnos-cli app install-fpk` 报 `app-center install has dependency app changes that require App Center UI`，**无 flag 可绕过**；
- 对**已安装应用**再次 `install-fpk`（任何包）直接 `{"code":10236}`，CLI 无 force/overwrite。

**原因** `[经验]`：平台把"会改动系统级依赖"视为强操作，命令行路径设了安全闸；UI 安装路径允许（先装依赖再装应用）。

**解法：同一份工程出两个包，差异只有一行** `[实测]`：

| 包 | `install_dep_apps` | 用途 |
|---|---|---|
| 测试包 | **无** | 真机 CLI 安装验证（CLI 只在这条路上可用） |
| 上架包 | `python312` | 应用中心 UI / 商店分发 |

构建脚本在**硬链接暂存目录**里重写 manifest（先删该行再按 profile 插回，打断硬链接，不动工作区）；两包 `manifest` 逐行 diff 只差 `install_dep_apps` 与 fnpack 自动生成的 `checksum` `[实测]`。

**双包线带来的证据义务（最容易被忽略）**：

> **「测试包安装成功」不能推出「上架包安装成功」。** 上架包多出依赖声明，且**从未真机安装**（CLI 无法模拟 UI 依赖安装路径）。对外表述只能是「测试包 `<sha>` 已完成真机安装验证；上架包仅差依赖声明一行，**尚未真机安装**」`[实测]`+`[经验]`。

### 3.4 幂等判定：版本号相同 ≠ 内容相同

**现象** `[实测]`：v2→v3 上游版本都是 `0.2.9b5`，但这一版给 wheel 打了补丁（CSP）。只比版本号的实现判定"无需重建" ⇒ 设备上跑的是**旧 wheel**，修复对升级用户完全不生效。

**根因** `[经验]`：包的应用版本号来自上游 `server/VERSION`，**与"wheel 内容是否变化"无关**。任何"在 wheel 层打补丁"的方案都会打破"版本号 ⇒ 内容"的假设。

**解法**：venv 建好后写指纹文件（如 `venv/.<app>-wheel.sha256`），记录安装时 wheel 的 sha256；`install/upgrade/main start` 三处都做「版本 **且** 指纹」双比对，不一致即重建；跳过重建与重建**分别打印原因**（`已就绪（…sha…）` / `重建原因：版本变化|wheel sha 变化`）`[实测]`。

**验证纪律**：验"全新安装"前先删 `<var>/venv`，否则验的是残留复用；验证新内容是否真进 venv，用**测试标记字符串**，不要用文件时间戳 `[经验]`（见 `dev-experience.md §3.5`）。

### 常见坑

1. **`install_dep_apps` 写进测试包**：命令行安装直接被拒，还会让人误以为"包坏了"。
2. **以为声明了依赖就不用手动加 PATH**：规范要求脚本里自己 `export PATH` `[规范] advanced §7`。
3. **wheel 层打补丁后只改内容不改 `RECORD`**：pip 装的时候报 hash 不匹配。补丁脚本必须重算 `RECORD`（sha256 + size）。
4. **拿"两个包字节数接近"当"内容一致"**：`app.tgz` 的 gzip/tar 时间戳元数据不同也会让整体 sha 不同；只能靠**逐成员比对**或关键文件 sha 比对 `[实测]`。

## 4. 数据目录与升级/卸载语义

**这一节解决什么问题**：搞清"谁在什么时机删了哪个目录"，否则会做出永远为真的错误判据，并给用户错误的"数据安全"承诺。

### 4.1 平台语义：手动安装 = 重装，并且清空 `data/`

`[实测]`（本项目 v6 真机，`DELIVERY-NOTES §3.21`）：

| 观测 | 值 |
|---|---|
| `@appdata/<app>/data` 目录 `btim` | 等于**安装时刻**，与 `logs/`、`run/`、`venv/` 同秒 |
| `data/config`、`agent/`、`team_control.db` | 应用**启动后**被重写（`team_control.db` 106 496 B → 4 096 B 空库） |
| `app.env`（`btim` 早于安装）/`home/`/`cache/` | **全部存活** |
| `appID` | 变化（例：50 → 52）⇒ 确实发生了"卸载 + 安装" |

**三条排除依据（说明为什么改应用代码修不好）** `[实测]`：

1. 不是应用初始化覆盖：`data` 目录 `btim` 是安装时刻，应用启动晚 2 分钟 ⇒ 旧数据在启动前已消失；
2. 不是卸载脚本删的：删除分支会同时删 `home/` 与 `app.env`，而两者都还在 ⇒ 分支未执行；
3. 不是"legacy 改名"逻辑：改名前会先判 `.fnos-app-meta` 标记，且未见 `data.legacy-*`。

**后果（必须写进用户文档）**：模型 API Key、用户自定义配置、历史会话与记忆**全部丢失**；向导里选"保留现有数据"**实测未能阻止**平台清空。

### 4.2 「清除数据」向导参数：形态不定，必须归一化

- 向导字段 `wizard_delete_data`，选项值 `"false"` / `"true"`（`wizard/uninstall`）`[实测]`；
- 但**平台注入到脚本里的值形态不定**：可能是字符串、布尔 `True`、`1`、`yes`、`on`，也可能未注入；
- 只做 `[ "$wizard_delete_data" = "true" ]` 判定 ⇒ 全部落到"保留"分支 ⇒ 清除承诺静默失效（本项目 P0-03）`[实测]`。

**正解**：`tr '[:upper:]' '[:lower:]'` 后 `case true|1|yes|on|y)`，**并把原值与解析结果都打印出来**——排查时"平台到底传了什么"是第一个要回答的问题。

`[实测]` 修复后的注入测试（`0.2.9-12`，`wizard_delete_data=True` 直接传参）：`原值='True' → 解析结果=1`，删除 7 项（`app.env` / `@apphome/<app>` / `data` / `venv` / `logs` / `run` / `pycache`），`rc=0`。即"大小写归一化"这一条就是修复前后的分水岭。

### 4.3 有效判据只有一个，且只在窗口内成立

> **判据**：卸载完成 → **重装之前**，`$TRIM_PKGVAR/app.env` 不存在（且 `$TRIM_PKGVAR` 目录空或不存在）。

三条理由缺一不可 `[实测]`+`[静态]`：

1. **`data/`、`home/` 会被 `mkdir -p` 重建** ⇒ "目录不存在"恒假失败；
2. **`app.env` 没有常规创建点**：只有"文件不存在时"由 `install_callback` 探测网关 uid 生成一次，是干净探针；
3. **但它也会被自动重建** ⇒ 判据**只在重装前的窗口内成立**。重装后再看，只能查旧数据残留（`data/config/.env`、`data/*.db`、`home/.<app>`）并用内容/时间戳区分新旧——成本高，只作兜底。

这条判据的演进过程本身就是教材（三个版本都被推翻过），见 `verify-experience.md §4.1` 与 `review-experience.md §6.3`。

> **与子文档的一处口径差异，以本文为准**：`dev-experience.md §6.6` 把这条写成"唯一标准：`app.env` 不存在"，没有带取证窗口；而 `QA-REPORT.md §12.4` 用代码证据指出"`install_callback` 在 `app.env` 缺失时会自动重建它" ⇒ **该判据只在"卸载完成 → 重装之前"成立**。少了窗口的版本会在重装后给出假通过/假失败。

### 4.4 升级通道：代码意图 ≠ 已验证行为

`[未验证]` `[实测]`

- 包内可以保留 `upgrade_init`/`upgrade_callback`（先 stop、重建 venv、不动 `data/`）；
- 但本项目该通道**在真机上从未走通**：CLI 对已装应用直接 `10236` 拒绝，应用不在商店也就没有"更新"入口；
- 因此**不要对用户承诺"有更新按钮且数据保留"**。已验证的只有"手动安装 = 重装 + 平台清 `data/`"。

### 4.5 设备历史残留：不删不覆盖

`[经验]`：数据目录可能与设备上既有内容冲突（本项目遇到过 `@appdata/jiuwenswarm` 已存在且非空）。做法：无自有标记文件（`.fnos-app-meta`）且目录非空时，整体改名 `data.legacy-<时间戳>` 保留，只记录不修改其它目录——先保住用户数据，再谈迁移。

### 常见坑

1. **拿 `data/`、`home/` 是否存在当"清除成功"判据**：必然假失败，然后大家去修一个没坏的地方。
2. **拿退出码当清除结果**：卸载脚本出于平台回滚风险会恒 `exit 0`，退出码不携带删除结果 `[实测]`。
3. **用 `ls` 无输出证明"已删除"**：无权限时也是空输出（假阴性）；要用 `[ -e ]` 并显式打印"仍存在"。
4. **在重装之后才去验收卸载清数据**：证据已被覆盖，只能记「未验证」。

## 5. 访问模型与 WebSocket 通道

**这一节解决什么问题**：把一个"只认根路径 + 自带 Origin 白名单"的现有 Web 服务，接进 fnOS 统一网关，并且让 WebSocket 真的通。

### 5.1 网关工作方式与入口声明

```
浏览器 → fnOS nginx(:5666/5667) 校验登录态 → ${TRIM_APPDEST}/<gatewaySocket>（UDS）
      → 应用侧桥 → 127.0.0.1:<内部端口>（真正的服务）
```
`[规范] advanced §2`：入口在 `app/ui/config` 用 `gatewayPrefix` 注册公开路径、服务监听 `gatewaySocket` 声明的 Unix Socket，转发时注入 `X-Trim-Userid` / `X-Trim-Isadmin` / `X-Trim-Username`。

本项目实测链路 `[实测]`：`浏览器 → nginx:5666 → app.sock → uds_gateway.py → 127.0.0.1:15173`（静态页 + `/api`），`/ws` 再按路径转发到内部 WS 端口。

### 5.2 前缀改写：只做字符串，不要解析 HTTP

**核心原则** `[实测]`+`[经验]`：桥只做三件事——**读头部 →（按需改写）→ 发头 → 双向纯字节 `_pipe`**。一旦开始"解析 HTTP 响应"，就要同时处理 `Transfer-Encoding: chunked`、`101 Switching Protocols`、WS 二进制帧、SSE 长连接，任何一处处理不当都是**静默截断**。

要点：

- 前缀剥离：`/app/<name>` → `/`，`/app/<name>/x` → `/x`；**拒绝任何 `..` 段**；根路径原样透传（不是错误）；
- **非 WS 请求强制 `Connection: close`**：防止 keep-alive 复用的第二个请求绕过前缀改写；
- **WS 请求必须保留 `Upgrade` / `Connection` 两个头**（其余 hop-by-hop 头照常丢弃）。

### 5.3 网关会改写 `Host`（这条会推翻一整类设计）

`[实测]`：v12 真机 `logs/ws-origin-last-match-x-forwarded.flag`，从未出现 `match-host`。

**推得的平台事实**：nginx 转发到 UDS 桥时把 `Host` 改写成回环/内部地址，**原始主机名只出现在 `X-Forwarded-Host` 一类代理头里**。

**硬含义（写进设计评审清单）** `[经验]`：

- **任何依赖客户端 `Host` 的校验在本平台都不可行**：基于 `Host` 的 CSRF 判定、CSP `connect-src` 生成、绝对 URL/回调地址拼接、WS 地址推导，全部会拿到回环值；
- 唯一带真主机名的是 `X-Forwarded-Host`，而它是**请求头、可伪造**——只能当"兜底依据"，不能当"安全边界"。

### 5.4 WebSocket 为什么"页面能开、消息发不出"

本项目踩了两次，两次判断都错（详见 `dev-experience.md §5`、`verify-experience.md §5`）：

| 次数 | 当初的判断 | 实际 | 推翻依据 |
|---|---|---|---|
| 1 | "fnOS 网关不支持 WS 升级" | 网关支持得很好；是**应用自己**的 Origin 白名单不含设备 IP/域名 ⇒ 403 | 把设备 IP 加进 `JIUWENSWARM_WS_ALLOWED_ORIGIN_HOSTS` 后立刻 101 `[实测]` |
| 2 | "同源判定用 `Origin == Host` 就够" | nginx 改写了 `Host` ⇒ 域名与 IP 会**一起 403** | 真机 flag 只有 `match-x-forwarded` `[实测]` |

**上游通常有两层 Origin 校验，语义并不对称** `[静态]`：

| 层 | 判定依据 | 无 `Origin` 时 |
|---|---|---|
| 第 1 层（HTTP 层） | `Origin` 与 `Host`/`outer_host` 比对（host+port），另有白名单兜底 | 放行（视为非浏览器客户端） |
| 第 2 层（agent/WS 层） | **只查白名单**，完全不比 `Host` | 默认拒绝，除非白名单含 `none` |

推论：**只改桥、只让 `Host` 变正确，只能救第 1 层**；第 2 层仍然只看白名单。要么给第 2 层打 wheel 补丁（维护成本高），要么维持"启动时把本机地址并入白名单"。`none` 不能删——TUI/SDK 这类不带 `Origin` 的客户端靠它才能连 `[实测]`。

### 5.5 桥内同源判定 + Origin 归一化（本项目最终方案）

**动机**：用户域名（DDNS、反代域名）不可预知；平台也不告诉应用"用户用什么域名访问"（`trim.system.getPlatformConfig` 只返回主题/语言/版本；`TRIM_*` 只有路径与标识；`app/ui/config` 的 `fnDomain` 是入口标识不是访问域名）`[静态]`+`[规范] open-api §5`。

**做法** `[实测]`：

1. **判定**：`Origin` 主机 == 候选主机之一。候选来源 = `Host` + `X-Forwarded-Host` + `X-Original-Host` + `X-Forwarded-Server`；
2. **分层（关键取舍）**：`Host` **必须恰好一条且可信时优先**；代理头**只在 `Host` 缺失或全为回环时兜底**——否则 `Host: nas.example.com` + `XFH: evil.com` + `Origin: evil.com` 会把判定基准稀释到任意请求头；
3. **判不出来就放行但要可见**：候选为空 ⇒ 放行 + `WARN fallback-allow` + 计数 + 分支标记，**绝不让新校验成为"功能唯一依赖未验证假设"**；
4. **归一化**：通过判定后把 `Origin` 改写为 `http://127.0.0.1` 再交上游（回环在上游两层白名单内）⇒ **上游那层 Origin 校验被旁路，真正判定在桥上**；
5. **只对 WS 生效**：普通 GET、静态特例、前缀改写都不受影响。

> **版本差异提醒（接手时先看包）**：`0.2.9-12` 实际落地的是"多条 `Host` 即拒"（M2），审查后已决定在 v13 改为"任一可解析非回环候选匹配即放行 + 诊断列全"（见 `anti-patterns.md AP-18`）。两者都在真实链路里验证过方向，但**不要对着一个包的 flag/日志去反推另一版的规则**。

**必须一起读的风险（否则会误以为"还有上游兜底"）** `[实测]`+`[经验]`：

- 归一化 ⇒ 上游校验被旁路；若桥"判不出来"又放行，则**两层在同一时刻同时失效**——"至少上游还在校验"这个直觉是错的；
- `Origin host == Host host` 允许"任何能解析到本机的域名"；DNS rebinding 页面可以做到 `Origin = Host = evil.com` **自洽通过**；
- 真正挡住 rebinding 的是后续四道门（域 cookie、网关注入身份头、管理员门、上游 token），**不能把这条校验宣传成"防 rebinding"**。

### 5.6 WebSocket 的可观测性设计（"读不到日志"环境下的正解）

`[实测]` 本项目最值钱的一块设计：

- 每次 WS 握手写一行：`origin / host / xfh / xoh / xfs` 的**实际值** + `allow|deny` + `reason`，同时落 `logs/ws-origin.log`（超限保留最近 200 行）；
- 每次判定覆盖写一个 **0 字节标记文件** `logs/ws-origin-last-<branch>.flag`，`branch ∈ match-host / match-x-forwarded / fallback / deny-<reason>`；
- 被拒时把同样判决写进 **403 响应体**（浏览器 Network 直接可见）。

**为什么用文件名而不是日志内容**：设备侧工具只能"列目录 + 看字节数"，读不到内容。`file ls logs/` 就能判分支 ⇒ **不需要用户复现、不需要 SSH**。这也是本项目在"日志全打码"环境下唯一能定性 `Host` 被改写的手段。

### 常见坑

1. **直接给现有服务加一层反代却不改 `Host` 语义**：上游所有"按 Host 拼 URL / 判同源"的逻辑都会错。
2. **把"支持 WS"当成"WS 一定通"**：差在应用自己的 Origin 白名单、base path、CSP、代理超时四个环节。
3. **只测 IP 不测域名（或反过来）**：本项目两次都是"IP 能开、域名不能用"，只测一边会得出反向结论。
4. **只用 `curl` 看状态码判断 WS**：未登录时连 `/app/<任意名字>` 都返回 `200` + 13 B `invalid token`（见 §8.2），状态码毫无判别力。

## 6. 安全模型：防线分工

**这一节解决什么问题**：把"谁防什么"写成表，防止后来人做代码瘦身时删掉一道"看起来冗余"的门。

### 6.1 防线分工表（本项目成品，节选完整版见 `review-experience.md §2.1`）

| # | 防线 | 位置 | **真正**防住什么 | **不防**什么 |
|---|---|---|---|---|
| 1 | 对端进程校验（`SO_PEERCRED` + exe 全路径 + 属主 + 父目录） | 桥 `_peer_allowed` | 本机**非网关进程**直连应用 socket | 经网关转发的请求；跨站页面 |
| 2 | 桥层 Origin 同源校验 | `_origin_decision` | **浏览器**从其它站点发起的跨站 WS | 伪造客户端（`Origin` 任意填）、DNS rebinding、`Host` 被改写时整体失效 |
| 3 | 管理员门（`X-Trim-Isadmin`） | 桥 `_handle` | 非管理员使用应用 | 伪造该头的客户端（依赖 #4） |
| 4 | 网关注入身份头 + 登录态 | fnOS nginx | 未登录访问；覆盖客户端自带的 `X-Trim-*` | 本机进程；网关配置错误 |
| 5 | 上游 Origin 两层校验 | 应用本体 | 白名单外 Origin | 桥已归一化 Origin 后对真实域名无判断力 |
| 6 | 上游 token 校验 | 应用本体 | 无有效 token 的请求 | 持有效会话者的越权（单用户实例无隔离） |

> **表头警示（必须保留）**：本表的首要用途不是解释，而是**防止误删**。要"优化/精简"任何防线前，先确认该职责是否还有别的防线承担。尤其——**DNS rebinding 是 #3/#4/#6 挡住的，不是 #2**；不能因为"已有 Origin 校验"就撤掉管理员门或放宽 token 校验。

### 6.2 peer 校验为什么不能"匹配进程名"

`[实测]` 三条反例（本项目 P0-01）：

| 判定方式 | 绕过手法 | 能不能用 |
|---|---|---|
| `/proc/pid/comm`（16 字节） | `prctl(PR_SET_NAME)` 任意进程自报 `nginx` | ❌ 只能写日志 |
| `basename(exe)` | `cp /usr/bin/python3 /tmp/nginx && /tmp/nginx` | ❌ |
| `realpath(exe)` 全路径 + 属主 `root` + 父目录非全局可写 | 需要能写 root 属主且父目录不可被任意用户写的路径 | ✅ |

**顺序同样重要**：peer 判定必须在**读任何请求字节之前**。理由：应用唯一的鉴权是"可信网关注入的 `X-Trim-Isadmin`"，而 `X-Trim-*` 任何本机进程都能伪造；只有先确认"对端确实是网关进程"，这个头才有意义 `[实测]`。

### 6.3 socket 权限：`0600` 会把网关锁在外面

`[实测]`：

- 网关 worker 与 app 用户 **uid 不同**（本项目 app uid <APP_UID>；网关侧 uid <GW_UID> 一类），`0600` 会让**真网关也连不上**；
- `chgrp` 要求"root 或本身是该组成员"，而 `config/privilege` 没有 `join-groups` ⇒ `os.chown(..., -1, gid)` **必定 EPERM**，配置了 gid 也收不紧；
- 正解是 **`0660` + `setfacl -m g:<gid>:rw <sock>`**（属主可对任意组授权，不需要自己是成员；天然支持多组）；`setfacl` 缺失或失败 ⇒ **回退 `0666` + WARN**，不能"收紧失败就拒绝服务"；
- `chmod` 必须在 `start_unix_server()` **之后**执行，否则被 `umask` 覆盖 `[实测]`。

**若最终仍是 `0666`**：把它写成"上架前必须闭环项 + 残余风险声明"，并在材料里说明 peer 校验已生效——**不要把做不到的条件写成硬阻断**（`review-experience.md §7.3`）。

### 6.4 残余风险清单（必须如实披露的几类）

| 残余项 | 性质 | 处置 |
|---|---|---|
| socket `0666` | 多一个"可连的面"，不是"可绕过" | 材料显式声明 + peer 校验佐证 |
| DNS rebinding 可过桥层 Origin 校验 | 设计使然（基准取自请求头） | 靠 #3/#4/#6 兜住，材料不得宣称能防 |
| 同机异端口页面可通过 Origin 校验（按 hostname 放行） | 需攻击者已能在同一 NAS 跑恶意 Web 服务 + 管理员已登录 | 知情接受，不排期（补丁维护成本 > 收益） |
| 依赖网关继续注入 `X-Forwarded-Host` | 平台升级若不再注入 ⇒ 退化为 `fallback` | 功能不退化、flag 可见、日志有 WARN |
| 单用户实例、多管理员不隔离 | 产品定位 | `desc` 与材料声明 |

### 常见坑

1. **把"权限位"当唯一安全判据**：`0666` 与"能通过 peer 校验"是两件事；反过来，"有 peer 校验"也不代表可以永远不收紧。
2. **用"上游还有校验"安慰自己**：桥做了 Origin 归一化后，上游那层对真实域名已经没有判断力（§5.5）。
3. **把 `X-Trim-Isadmin` 当可信身份**：它只是普通请求头，可信前提是"对端是网关"（#1）。
4. **安全规则只写"要严格"不写"防谁"**：本项目曾把"多 `Host` 即拒"当必须硬化项，实测收益≈0、代价是可能 100% 拒掉正常反代，最后撤回（`review-experience.md §5.1`）。

## 7. 构建与发布流程（含防御性闸门）

**这一节解决什么问题**：保证"测的包 = 交付的包 = 修好的代码"，并让上架材料经得起逐条核对。

### 7.1 三道闸门（每一道都由一次事故逼出来）

| 闸门 | 防什么 | 实现 | 失败行为 |
|---|---|---|---|
| 补丁闸门 | "包能打出来、但补丁没生效" | 补丁脚本 `--check`：目标常量不存在/出现多次即报错 | `exit 1`，中止构建 |
| 新鲜度闸门 | "改了代码却打进旧包" | 解包 `app.tgz`，把 `cmd/*`、`app/ui/config`、`app/server/*`、`wheelhouse/*.whl` 与工作区**逐字节 sha256** 比对 | 打印不一致条目并 `exit 1` |
| profile 断言 | "测试包带上架包的依赖行（或反之）" | 构建后检查 manifest 是否含 `install_dep_apps` 与预期一致 | `exit 1` |

**新鲜度闸门的事故原型** `[实测]`：`supervisor.py` 17:24 改好，包 17:06 就打完了；设备上跑的是旧文件，**整整一轮排查指向错误方向**。逻辑 review 看不出这件事，时间戳也会被硬链接/复制弄乱——只有逐字节比对能抓到。

### 7.2 打包命令的两个环境坑

`[实测]`

1. **`fnpack build` 把 `.fpk` 写到"当前工作目录"**，与 `-d` 参数无关 ⇒ 必须在暂存目录里 `cd` 再执行；
2. **`/tmp` 可能满**（本项目 `/tmp` 是 5.8 G tmpfs，解 126 MB `app.tgz` 就写满，后续文件变 0 字节、`sha256sum` 全部返回 `e3b0c442…` 空文件指纹）⇒ 构建与取证都显式指定大分区 `TMPDIR`，大文件一律**流式**（`tar -xzO <member> | sha256sum`），不落盘。

### 7.3 版本与发布纪律

`[实测]`+`[经验]`

- **同一版本号永不重发**；每次改动都要有新版本号（本项目 `0.2.9-5` → `0.2.9-12` 每次出包递增）；
- **`fnpack` 只接受 `x.y.z[-r]`**，拒绝 `-beta.N`（本项目实测），所以"上游 `0.2.9.beta5` + 平台修订号"这种映射要写进材料；
- **除 P0 不重打包**：每打一次就产生新 sha，所有"证据 ↔ 包"的绑定全部要重做；判"是否值得重打包"看三点：功能可用性 / 安全边界 / 数据安全；
- **文档不进包**：改文档不影响包 sha，"文档同步"和"出包"是两件事。

### 7.4 证据绑定：四要素缺一即"未验证"

`[实测]`+`[经验]`：每组结论必须同时记录 **`包 sha256` + `关键脚本 sha256` + `执行账号（含 uid）` + `原始命令与原始输出`**。

没有 sha 的结论，一周后就无法证明它属于哪个版本；本项目出现过两次"差点把旧包结论套到新包上"。同时要守**同包原则**：安全项与可用项必须来自同一个包 sha，禁止"安全项在新包验、可用项在旧包验"合并计通过。

### 7.5 上架材料的一致性审查（不产生新 bug，但影响商店里每一句话）

必查四类 `[实测]`：

1. **声明 ↔ 实现**：如"仅管理员可用" ↔ `require_admin`、`disable_authorization_path=true` ↔ 实现确实不用授权路径；**不得声称未实现的功能**（`[规范] dev-guide §4` 明写 `desc` 必须准确）；
2. **体积声明 ↔ 构建产物**：本项目安装卷 ≈0.5 GB、数据卷 ≈2 GB、升级峰值 ≈3–3.8 GB（wheelhouse 467 MB + 装后 venv ≈1.5 GB）；
3. **测试材料 ↔ 同一版本**：截图/日志不得来自旧版包；
4. **未验证项必须显式声明**：上架包未经真机安装、协议层 101 未取得，都要写在材料里，不能省。

### 7.6 判定口径：三选一，条件必须可证伪

`[经验]`：**当前可上架 / 有条件可上架（列出条件）/ 不可上架**。禁止"修复后可上架"这类留余地表述。

"有条件可上架" = 代码侧无未修 P0/P1，剩下的是**用一条命令就能证伪的待证事实**，且为负时结论直接翻成"不可上架"。本项目两条条件：① 非管理员伪造 `X-Trim-Isadmin` 是否被拒；② 卸载选"清除"后窗口内 `app.env` 是否消失。

### 常见坑

1. **拿"构建成功"当"包是对的"**：两者之间必须有一个**能失败的**独立校验。
2. **补丁匹配不到就跳过继续构建**：这是最危险的行为——包能发出去，但修的是空气。
3. **sha 与字节数来自不同次构建**：`ls -l` 与 `sha256sum` 必须在同一批命令内取。
4. **把"已验证"的范围说大**：测试包验过 ≠ 上架包验过；行为证据 ≠ 协议证据（§8.4）。

## 8. 调试与取证工具箱

**这一节解决什么问题**：在"没有 shell、读不到日志内容、不能升级、不能带向导卸载"的环境里，仍然能给出有证据强度的结论。

### 8.1 先认清工具边界（`fnos-cli` 实测）

`[实测]` 逐条见 `verify-experience.md §1`，这里只列会改变方案的四条：

| 能力 | 结论 |
|---|---|
| 升级已装应用 | ❌ `app install-fpk` → `code 10236` |
| 带向导卸载 | ❌ `requires custom wizard parameters; run it from App Center UI` |
| 读文件内容 | ❌ 无 `file cat`；`file download-url` 与 raw 通道都返回 `uri=[REDACTED]` |
| 读日志内容 | ❌ `file search` 只匹配文件名；`logger list` 返回 0 条 |
| 列目录 | ⚠️ app 私有目录必须用 `file ls`，`ls-dir` 返回 `[]`；`@appdata/<app>` 根还会**漏项** |
| 装包耗时 | ⚠️ CLI 等待窗口 ≈208 s，建 venv 装 262 wheel 超时 ⇒ **必报超时但设备侧继续并成功** |

⇒ 验收必须"借用户动作 + 用元数据取证"，不能自己制造场景。

### 8.2 HTTP 侧：状态码几乎没有判别力

`[实测]`：

- 未登录访问 `/app/<app>`、`/app/<app>/ws`、甚至 `/app/doesnotexist` —— **一律 `HTTP 200` + `text/plain` + 13 B `invalid token`**（前缀级兜底）；
- 非 `/app/` 前缀才走 404；
- **WS 升级请求也一样**：补齐 `Connection: Upgrade` / `Upgrade: websocket` / `Sec-WebSocket-Version` / `Sec-WebSocket-Key` / `Origin` 后，仍是 `200` + `Server: nginx` + 13 B ⇒ **鉴权先于桥，无会话拿不到 101**。

**正确判据**：看响应体、`Content-Length`、`Content-Type`、`Server`。

**谁返回的**：`Server: nginx` ⇒ 请求没到应用（主站/网关处理）；**无 `Server` 头** ⇒ 自建桥自己拼的响应。这条比"看现象猜"快得多。

### 8.3 六把尺子（读不到内容时的替代观测）

`[实测]` 完整版见 `verify-experience.md §2`，推荐顺序：

```
存在性(file prop 直指文件) → 尺寸/时间(btim/mtim) → 文件名编码(flag) → 端口/响应头 → 进程 uid
```

- **存在性**：`file prop <path>` 非 `errno` 即存在；**判"不存在"必须直指文件路径**，不能靠目录列举（会漏项）；
- **`btim`/`mtim` 差分**：`btim == mtim` 且等于某事件时刻 ⇒ 走了 `os.replace` 原子替换（新 inode），而不是追加写；
- **文件名编码分支**：把判定分支写进 0 字节文件名（`*-match-x-forwarded.flag` / `-fallback.flag` / `-deny-mismatch.flag`），只靠 `file ls` 就能判分支；
- **差分（对照组）**：任何"是否变化"都要有装前基线，且基线必须与被测对象**同一生命周期**（对象被重建后基线要换）；
- **端口**：`curl -w '%{http_code} %{size_download}'`，`http_code=000` 是**连接层失败**（如对明文端口发 https），不是"应用 500"。

### 8.4 证据分级与表述纪律

| 等级 | 定义 | 本项目实例 |
|---|---|---|
| **协议证据** | 直接观测到协议层事实 | DevTools 里 `/ws` 返回 **101** |
| **行为证据** | 只能观测到功能层"能用/不能用" | 用户"能发能回"、消息双向收发 |
| **静态/推断** | 代码可查但未在真实环境观测 | "按代码看这条会被拒" |

**纪律**：行为证据 ≠ 协议证据。本项目最终结论只能写"IP 与域名均可用，WS 判定走 `match-x-forwarded`，桥层校验生效未降级"，**不能写"已验证 101"**；反过来，拿不到 101 也不否定可用性，只需标清等级。

### 8.5 判"工具缺陷"而不是"设备事实"

`[实测]` 本项目判错 5 处（`verify-experience.md §6`），共同模式是**把"工具的沉默"当成"对象的属性"**：

- `ls-dir` 返回 `[]` → 不是 ACL 限制，是工具口径（换 `file ls` 即可）；
- 目录列举漏项 → 不是"不存在"；
- 偶发 `errno 4100` → 假阴性，换时间点重试再下结论。

**通用规则**：**工具的"空结果"只能产出"未验证"，不能产出"不存在"。** 先换等价命令复核，再下结论。

### 常见坑

1. **用字节数反推"某行被加了什么"**：日志各分支行长只差 1–3 B、且 `Host` 真值未知时，差分等于噪声（`verify-experience.md §2.2` 有正例与反例）。
2. **基线取"上一版的字节数"**：对象被重建后（如 `data/` 被平台清空），基线要换成模板原值。
3. **拿 `file access` 当文件 mode**：它返回的是调用方权限掩码，不是 mode 位。
4. **`monitor proc-list` 刚装完就读**：有缓存延迟，会读到上一轮 pid；`stop` 一次或等待后重读。

## 附：一句话版本（给赶时间的人）

1. **先定访问模型**：常驻 + WS + 要登录态 ⇒ 统一网关；端口型的代价是无 TLS、混合内容、LAN 无鉴权。
2. **网关会改写 `Host`** ⇒ 一切"按 Host 拼 URL / 判同源"的设计都会失效。
3. **卸载脚本**：不 `source` target、参数归一化、删除 fail-open、恒 `exit 0`、路径三重校验。
4. **判据只能选"只有该动作才会改变"的量**（`app.env` 是否存在），且要写在**窗口内**。
5. **幂等比内容**：venv 指纹记 wheel sha256，因为"版本号相同"经常意味着"内容不同"。
6. **构建三闸门**：补丁 `--check`、包内 vs 工作区逐字节、profile 断言。
7. **证据四要素**：包 sha + 脚本 sha + 账号 uid + 原始输出；行为证据不许写成协议证据。
