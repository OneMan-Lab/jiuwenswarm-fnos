# 架构说明：JiuwenSwarm 作为 fnOS 原生应用的接入设计

> 本文是**公开版架构说明**：只讲机制、取舍与代价，不含任何实测值（无内网地址、无域名、无运行属主编号、无机型/内核/卷号）。
> 真机取证报告（含真实标识）不随仓库发布；本文所述结论凡是"仅本地/脚本级验证"的，均在文中显式标注。

---

## 0. 一句话概括

> fnOS 的**统一网关**负责登录态校验，应用只能通过**一条挂在自己目录下的 Unix Domain Socket** 被访问；
> 而要被托管的这个应用是"常驻服务 + WebSocket"的形态，只会监听 TCP。
> 因此本设计的最小必要组件是：**一个把 UDS 请求转成 TCP 请求的桥（前置）**，外加**一套不依赖客户端 `Host` 的同源判定**与**一套平台能接受的卸载语义**。

---

## 1. 整体链路：为什么必须有一个 UDS → TCP 桥

### 1.1 链路

```
浏览器
  │  HTTPS/HTTP（fnOS 门户端口）
  ▼
fnOS 统一网关（nginx，持有登录态，负责鉴权）
  │  proxy_pass → unix:<应用目录>/app.sock
  ▼
桥 uds_gateway（本应用自带，监听 UDS）
  │  ① 对端身份校验  ② 管理员门禁  ③（WS）同源判定  ④ 请求行前缀归一
  │  127.0.0.1:<内部端口>（回环 TCP）
  ▼
应用本体（app_web，只监听回环 TCP，提供 HTTP + WebSocket）
```

### 1.2 为什么必须有桥

| 事实 | 后果 |
|---|---|
| 平台只把请求转发到**应用目录下的 UDS**（`app.sock`） | 应用侧必须有人在 UDS 上 accept |
| 应用本体（上游）**没有 Unix Socket 监听能力**，只会监听 TCP | 无法直接把 `app.sock` 交给上游 |
| 应用本体**只认根路径 `/`**，不认网关前缀 | 需要有人把 `/app/<app>/…` 归一成 `/…` |
| 上游是常驻服务 + 长连接（WebSocket/SSE），不是 CGI | 不能走"每请求起进程"的 CGI 形态（CGI 承载不了长连接） |

**桥做的最小工作**恰恰是这四件事：接受 UDS 连接 → 判定对端可信 → 归一请求行前缀 → 与上游回环 TCP 做**原始字节双向透传**。
因为只改请求行、不动其余字节，**WebSocket 升级与数据帧无需任何特判**（`Upgrade`/`Connection`/`Sec-WebSocket-Key` 原样保留）。

### 1.3 如果不做桥，会缺什么

- 把上游改成监听 UDS：**不可行**（上游无此能力，且上游是与平台无关的通用组件，不应为单一平台改写）。
- 用 CGI 包一层：**丢失长连接**（WebSocket 无法在"每请求一进程"模型下工作），聊天/流式输出直接不可用。
- 改用"端口服务型"直接暴露上游：绕开了网关鉴权，见 §6。

## 2. WebSocket 同源校验：为什么必须依赖 `X-Forwarded-Host`

### 2.1 机制

上游对 WS 握手做 Origin 校验，判定方式是**主机名精确匹配白名单**（默认只含回环与 `localhost`/`none`）。
经统一网关访问时，浏览器带的 `Origin` 是**用户实际访问的主机名**（设备地址或自定义域名）。

平台侧的实测事实是：**网关在转发时会改写 `Host`**，把原始主机名放进 `X-Forwarded-Host` 一类代理头。
因此：

> **任何"只信任客户端 `Host`"的同源校验，在该平台上都会先失效** —— 它看到的是被改写后的内部值，与浏览器 `Origin` 永不相等，
> 结果是**连本来可用的路径也一起被拒**。

这不是"多加一层保险"，而是**校验能不能成立的前提**。

### 2.2 设计

1. **判定基准取候选集合**：`Host` 优先；仅当 `Host` 缺失或只剩回环时，才回退到 `X-Forwarded-Host` / `X-Original-Host` / `X-Forwarded-Server`。
   （顺序很重要：若无条件混用，`Host` 为真、代理头被伪造时基准会被"稀释"。）
2. **端口规则**：任一侧缺端口、或相等、或候选侧为 80/443 → 视为匹配（避免默认端口省略导致的假阴性）。
3. **通过后归一化转发**：把 `Origin` 改写为 `http://127.0.0.1` 再交给上游（回环本就在上游白名单内）。
4. **判不出来就不拦**：当所有候选都缺失或只剩回环时，**不拒绝**，仍归一化转发。

### 2.3 取舍与代价（必须一起读）

| 设计 | 好处 | 代价 |
|---|---|---|
| 归一化 `Origin` 后转发 | 上游两层校验自然通过，域名/地址变化无需预知 | **上游那层 origin 校验被旁路**，真正的判定只剩桥的这一层 |
| 判不出来就不拦 | 网关行为变化时**不至于把可用功能弄挂** | 该请求上**两层防线同时失效** —— "至少上游还在校验"这个直觉是错的 |
| 基准取自请求头 | 无需平台提供访问域名（平台不提供） | **DNS rebinding 残余风险**：rebinding 页面可构造 `Origin == Host` 自洽通过。真正兜底的是后续四道门（域 Cookie、网关注入的身份头、管理员门禁、上游 token）。**因此不得把这条校验宣传成"能防 rebinding"** |
| 允许多来源候选 | 兼容"改写 Host + 附带代理头"的现实 | 「任何解析到本机的域名都放行」等价于放弃"只信任已知域名"；跨域 Cookie 不随请求发送 + 网关鉴权在前，风险可接受但需记录 |

### 2.4 可观测性设计（在"读不到日志"的环境里判断分支）

判定结果不只写日志，还**编码进文件名**：每次 WS 判定后覆盖写一个 **0 字节标记文件**，名字即分支
（如 `match-host` / `match-x-forwarded` / `fallback` / `deny-<reason>`）。
理由是：很多托管环境下只能看到"文件是否存在、多大"，看不到内容 —— 文件名是**最便宜的远程可观测通道**。
被拒时同时把判定依据写进 **403 响应体**，让排障者能在浏览器里直接看到，而不必翻日志。

> 这条设计的价值在真机上被验证过：正是靠"标记文件名"，才确认了判定走的是代理头分支而非"降级放行"。

## 3. 启动前并入本机地址：为什么白名单要由应用自己写

### 3.1 问题

上游的 Origin 白名单默认几乎是空的（回环 + `localhost`）。首次启动时：

- 用户通过设备地址访问 → 浏览器 `Origin` 是设备地址 → **不在白名单** → WS 握手被拒；
- 表现是"页面能打开、HTTP 正常，但聊天一直断开" —— 很容易被误判成前端或网络问题。

### 3.2 设计

`supervisor` 在**拉起子进程之前**做三件事：

1. **收集**：本机所有网卡的 IPv4（两条独立路径取并集：`ioctl` 取址 + `ip -4 -o addr`，后者缺失则忽略）
   ＋ 主机名 ＋ FQDN ＋ 已有环境变量 ＋ 用户在配置文件中已有的自定义值；
2. **合并写回**：以"**只增不减**"的方式并入配置文件里那一行白名单，原子替换、保留原权限；
3. **断言**：把"白名单里是否含非回环地址"打进启动日志，避免再次出现"看起来配了、其实全是回环"。

### 3.3 两个容易踩的点

| 点 | 原因 |
|---|---|
| **必须写配置文件，不能只设环境变量** | 上游启动时用 `load_dotenv(..., override=True)` 读配置文件，**会覆盖继承来的环境变量** ⇒ 只设 env 等于没设 |
| **不能靠"主机名反查 IP"** | 多网卡设备上反查通常只返回一块网卡（甚至返回回环）；必须**枚举网卡**才能拿到用户实际访问的那个地址 |
| **写入时机必须在子进程之前** | 子进程启动时才读配置；晚于启动就没意义 |

### 3.4 已知不完美

- 枚举会把**虚拟网卡/隧道地址**一起并入（如容器网桥、VPN 网段）。因为校验是"主机名精确匹配"且这些地址外部不可达，风险很低，属"宁多勿少"的取舍。
- 自定义域名**无法**由应用自动获知（平台不向应用暴露"用户访问域名"），只能由使用者显式写入配置项。这也是 §2 桥内判定方案存在的原因：**不依赖预知域名**。

## 4. 卸载与数据清除：为什么设计成 fail-open + 恒 `exit 0`

### 4.1 两个不同性质的要求

| 类别 | 语义 | 理由 |
|---|---|---|
| **参数校验** | **fail-fast（硬中止）** | `TRIM_PKGVAR` 为空、目标非绝对路径、目标不在允许范围 → 立即退出、一个文件都不删。`rm -rf ""` / `rm -rf /` 必须**不可能**发生 |
| **删除动作** | **fail-open（逐项继续）** | 某项删不掉只记 `WARN` 并继续删其余，最后汇总「已删 N / 残留 M + 原因」 |
| **退出码** | **始终 `exit 0`**（参数非法除外） | 卸载脚本返回非 0 会被平台判为"卸载失败"，可能触发回滚或报错 |

### 4.2 代价（如实写出来）

- **`exit 0` 意味着"删除失败"不会自动上报给用户界面**：只能靠卸载日志/残留清单发现。这是为了让卸载流程本身不被判失败而做的交换。
- **fail-open 意味着可能"删不全"**：宁可漏删一项并告警，也不能因为一项失败把剩下的都留下。
  反过来说，**"删一半就退出"比"完全不删"更危险**——用户看到卸载成功、部分数据确实没了，会以为清干净了，而最敏感的文件可能仍在。
- 因此删除顺序按**隐私优先**：含凭据的配置 → 用户数据目录 → 应用数据目录 → 运行期产物（虚拟环境、日志、进程信息、缓存）。

### 4.3 一个真实踩过的坑（供后来者避雷）

平台传入"是否清除数据"的向导参数时，**形态未必是字符串 `"true"`**（可能是布尔、大小写变体、数值，或根本没注入）。
若脚本用 `[ "${flag:-false}" = "true" ]` 这种严格字符串比较，就会**静默走"保留"分支，一个文件都不删**，而用户界面显示"已清除"。
修法：**归一化取值**（大小写不敏感，接受 `true/1/yes/on/y`）＋**打印原值与解析结果**，让下一次卸载能一次性定性。

> **结论强度**：脚本级已用多组输入自测通过；**真机上的独立卸载重验尚未完成**（受平台限制，卸载只能由用户在应用中心触发）。
> 因此当前状态应表述为"**代码已修、脚本级通过、真机卸载未重验**"，不写成"已验证"。

### 4.4 平台语义须知（容易被用户误解为缺陷）

实测结论：**在应用中心对"已安装的应用"再次手动安装，等价于卸载 + 安装**，平台会在该流程里清空应用的**数据目录**，
而**不**清空应用根目录下的其它文件（如运行配置、用户 home、缓存）。因此：

- 应用侧**无法**通过"启动时检测到已有数据就跳过初始化"来规避——数据在应用启动前就已被平台清掉；
- 这属于平台安装语义，不是包缺陷；发布说明必须告知用户"升级前自行备份数据目录"；
- "保留数据升级"的通道（升级回调）在包内存在，但**真机未验证**（平台不允许通过命令行升级已装应用，商店中亦无此应用），**因此不对外承诺"更新按钮"**。

## 5. 双包线的由来（0.2.9-12 起已取消，仅出应用中心包）

> **状态**：本节是历史背景。自 0.2.9-12 起构建只出应用中心包（`install_dep_apps` 恒在），代价是放弃命令行自动化安装闭环，决策记录见 `docs/BUILD.md §3.1`。下方表格与论证仅解释历史为什么分开，不再代表当前策略。

| 项 | 测试包 | 上架包 |
|---|---|---|
| 依赖声明 `install_dep_apps` | **不含** | **包含**（如 `python312`） |
| 其余内容 | 逐字节一致（同一 `app.tgz`、同一批回调、同一批图标） | 同左 |
| `checksum` | 随 manifest 自动变化 | 同左 |
| 安装路径 | 可在受控环境用命令行安装 | **必须经应用中心 UI**（依赖声明会触发"需要 UI 处理依赖变更"的拒绝） |

**为什么当初要分开**：带依赖声明时，自动化通道会被依赖闸拒绝，无法完成"装→验→卸"的自动化闭环；
而不带声明又不能满足应用商店"声明运行时依赖"的要求。**两条需求互斥，只能出两个包。**

**结论强度**：测试包的真机安装/启停/入口已多次验证；**上架包（含当前唯一产物）的真机 UI 安装（含依赖自动安装）未验证**，
上架前必须在真机应用中心走一次。

## 6. 访问模型选型：为什么最终是"纯网关型"，而不是"端口服务型"

| 候选 | 否决理由 |
|---|---|
| **index.cgi（CGI）** | 每请求起进程，**承载不了常驻服务与长连接**；本项目核心功能是流式对话，必须有 WebSocket |
| **端口服务型** | ① 直接暴露一个 LAN 端口，**绕过 fnOS 登录态**；② 上游 Web 模式在"访问令牌为空"时**不做任何校验**，等于把智能体无认证地放给全网；③ 上架门禁将其判为 P0 |
| **纯统一网关（选定）** | 鉴权完全由平台负责；不新增 LAN 端口；不改变用户"打开应用"的既有习惯 |

**代价（如实记录）**：一切都要经过桥 ⇒ 需要自己解决"对端身份可信""同源判定""请求行前缀归一"这三件事；
且**必须依赖平台网关的转发行为**（会改写 `Host`、附带代理头）。这些行为是平台实现细节，**平台升级后可能变化** ——
这也是本设计坚持"判不出来就不拦 + 分支可观测"的原因：**把"平台行为变化"的后果从"功能中断"降级为"安全等级下降且可见"**。

| 上架包经应用中心 UI 安装（含依赖自动安装） | **未验证** |
| 未授权访问被网关拦截（不出现应用内容） | **已验证**（未登录请求被平台拦在网关层） |

## 8. 设计不变量（改动时不可破坏）

1. **鉴权不依赖可伪造的请求头**：管理员头只在"对端身份已可信"之后才有意义；对端判定必须在**读取任何请求字节之前**完成。
2. **校验失败要"可见地降级"**：降级放行必须同时留下 WARN 与分支标记，否则"能用"会被误读成"校验生效"。
3. **桥只做最小改写**：只允许改请求行前缀与（WS 的）`Origin`；其余字节双向透传 —— 这是 WebSocket/SSE 免特判的前提。
4. **数据目录只落在框架注入的路径下**：临时目录、缓存、日志、家目录均显式指向框架变量，不往数据卷之外落文件。
5. **删除类脚本**：参数 fail-fast、删除 fail-open、退出码恒 0、顺序隐私优先（见 §4）。
6. **交付物与工作区必须逐字节一致**：包内脚本/前端产物要与构建输入相同，否则会出现"改了代码却发了旧包"的事故
   （构建新鲜度闸门即为防止这类事故而存在）。
